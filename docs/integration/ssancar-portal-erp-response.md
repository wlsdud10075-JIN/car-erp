## 0. 결론 3줄

1. **접속 방식은 §4 안 A(DB 직접 조회)가 아니라 안 C(HMAC API)다.** 우리는 이미 같은 구조의 읽기 API를 **1년 가까이 운영 중**(board 연동)이라, 새로 만드는 게 아니라 **스코프 축 하나를 추가**하면 된다.
2. **대상 ERP는 heymanerp(`heysellcar.com`) 하나로 확정.** 파일럿 바이어 `ATLAS GROUP SH.P.K` 를 3사에서 검색해 **heymanerp `buyers.id = 13`** 에서 찾았다. (ssancarerp 에는 없다 — 바이어 9사·차량 15대뿐.)
3. **쟁점은 필드 매핑이 아니라 아래 3개다.** 셋 다 매핑표로 흡수되지 않는다.
   - **① 선적 이후 상태가 없다** — 포털 11단계 중 **8~11(ON_BOARD·IN_TRANSIT·ARRIVED·DELIVERED)** 이 전부 `거래완료` 하나로 붕괴한다. 그 `거래완료` 가 **239대 중 100대(42%)** 다. (§3)
   - **② 포털은 「FOB·USD」 전제인데 우리 실거래는 「CFR·EUR」 이다** — 판매차 235대 중 **CFR 219 / FOB 0건**, 통화는 **EUR 190 · USD 34 · KRW 11**. SSP 적립이 FOB USD 기준이면 **두 번의 변환**(운임 분리 + 환산)이 필요하다. (§4.2)
   - **③ `paid_at` 을 그대로 적립 트리거로 쓰면 못 받은 돈에 크레딧이 적립된다** — 손실처리·상계로도 완납 판정이 난다. (§4.2)

## 1. §4 접속 경로 — 안 A를 쓸 수 없는 이유 (거절이 아니라 대체안 제시)

포털 문서는 안 A(사이트 서버 → ERP DB 직접 조회)를 권장했다. 세 가지 이유로 불가하고, **그보다 나은 경로가 이미 가동 중**이다.

| # | 안 A가 막히는 지점 |
|---|---|
| ① | **RRN(주민등록번호)은 애플리케이션 키로 암호화**돼 있다(`nice_reg_owner_rrn`). DB를 직접 읽어도 복호화되지 않는다 — 즉 DB 직결은 "더 많이 보는" 경로가 아니라 **일부는 아예 못 읽는** 경로다. |
| ② | **IDOR 격리·PII 화이트리스트가 전부 애플리케이션 레이어에 있다.** 누가 어느 차를 볼 수 있는지, 어떤 필드를 응답에 실을 수 있는지가 코드에 있고 DB엔 없다. DB 직결은 그 통제를 **전부 우회**한다. |
| ③ | **회사가 3개다**(heymanerp·ssancarerp·karabaerp, 서버·DB 각각). DB 직결은 회사마다 계정·보안그룹·스키마 드리프트를 각각 관리해야 한다. |

### 대체안 = 안 C. 이미 있는 것

`board`(영업용 앞단 앱)가 **HMAC 서명 GET API**로 car-erp를 읽고 있다. 권위 스펙 = `docs/integration/board-portal-api.md`.

- 인증: 요청 서명(`METHOD + PATH + 정렬된 쿼리 + 타임스탬프 + 바디`) + 5분 시간창 + nonce 재사용 거부
- 격리: 호출자 식별 → **서버가 스코프를 강제**(호출자가 범위를 못 넓힌다)
- 응답: **화이트리스트** — RRN·소유자명/주소·계좌·마진 원값은 어떤 응답에도 안 나간다
- rate limit·감사로그 포함

**포털이 필요로 하는 건 이 구조의 스코프 축을 「영업」에서 「바이어」로 바꾼 한 벌**이다. 인증·감사·PII 통제는 그대로 재사용한다.

> Q9(보안그룹 개방) 답: **불필요하다.** API는 HTTPS 공개 엔드포인트 + 서명 인증이라 IP 개방이 필요 없다. 굳이 원하면 IP allowlist는 추가로 얹을 수 있다(선택).

> 근거는 파일럿 바이어 1건이므로 정확히는 **「파일럿 기준 heymanerp」** 다. 위 21사를 포털 274사와 대조해 겹치는 쪽이 heymanerp 하나뿐인지 확인하면 확정된다. (`10 R.S.H` 는 뒤에 공백이 붙어 있다 — 매칭 전 TRIM 필요.)

⚠️ **파일럿 데이터가 얇다.** ATLAS GROUP 귀속 차량은 **2대**다(포털 스텁은 12대). 파일럿 검증은 되지만 화면이 비어 보일 것이다 — 바이어를 하나 더 고르거나(거래량 상위) 기대치를 조정할 것.

### 바이어 식별자 (Q2)

**전용 코드 체계가 없다. `buyers.id`(정수)가 유일 식별자다.** 따라서 포털 `ssc_buyers.erp_buyer_code` 에 저장할 때는 **회사 접두사를 붙일 것**:

```
heymanerp:13     ← ATLAS GROUP SH.P.K
```

지금은 1사만 연동하지만, 접두사 없이 `13` 만 저장하면 다른 회사가 붙는 순간 **조용히 충돌**한다(3사 id가 각각 1부터 시작).

## 3. 🚨 최대 쟁점 — 포털 11단계 중 8~11이 ERP에 없다

ERP 진행상태는 저장 컬럼이 아니라 **아래 규칙으로 매번 계산**되는 값이다. 규칙의 첫 줄이 `B/L 문서가 있으면 → 거래완료` 다. 즉 **B/L이 발급되는 순간 그 차는 영원히 「거래완료」** 이고, 그 뒤의 선적·항해·도착·인도는 ERP가 추적하지 않는다.

| # | 포털 코드 | ERP 대응 | 판정 |
|---|---|---|---|
| 1 | WON (Purchase Confirmed) | `판매중` | ✅ |
| 2 | AWAIT_PAY | `판매중` + 미수 > 0 | ✅ 파생 |
| 3 | PAID | `판매완료` (미수 ≤ 0) | ✅ |
| 4 | INSPECTING | — | ⚠️ ERP 없음 (board 검차 영역) |
| 5 | DOC_PREP | `말소완료` / `통관중` 근사 | 🔶 근사 |
| 6 | AT_YARD | `선적중` (반입지 입력) | ✅ |
| 7 | AWAIT_SHIP | `선적완료` / `통관중` | 🔶 근사 |
| 8 | ON_BOARD | **`거래완료`** | ❌ 구분 불가 |
| 9 | IN_TRANSIT | **`거래완료`** | ❌ 구분 불가 |
| 10 | ARRIVED | **`거래완료`** | ❌ 구분 불가 |
| 11 | DELIVERED | **`거래완료`** | ❌ 구분 불가 |

**운영 실측 (heymanerp 239대)** — 거래완료가 압도적 다수다:

```
거래완료 100 · 선적완료 77 · 판매완료 31 · 통관중 17 · 판매중 8 · 말소완료 3 · 선적중 2 · 매입중 1
```

### 부분 구제책과 그 한계

`shipping_date`(출항일 220건) · `eta_date`(도착예정 214건)가 있어서 **날짜 비교로 8·9·10을 근사**할 수 있다:

- `오늘 < ETA` 이고 출항일 있음 → IN_TRANSIT
- `오늘 ≥ ETA` → ARRIVED (추정)

다만 **ETA는 예정일이지 실적이 아니다.** 지연되면 포털은 "도착함"이라고 표시하는데 배는 바다 위에 있다. **DELIVERED(11)는 어떤 방법으로도 파생 불가** — ERP에 인도 확인 개념이 없다.

### 그 외 없는 것

| 포털 필드 | 상태 |
|---|---|
| `status_entered_at` (현 상태 진입 시각) | ❌ **전이 이력이 없다.** 현재값 1개만 저장된다. |
| `expected_next_at` (다음 단계 예상일) | ❌ 없음 |
| `eta_history` (ETA 변경 이력) | ❌ 없음 (현재값만) |
| `bl_sent_at` / `courier_no` (B/L 원본 발송·DHL 송장) | ❌ **DHL은 발송 신청 여부 체크박스만** 있고 송장번호 칸이 없다 |

> ⚠️ `bl_issue_date`(B/L 발급일)는 컬럼은 있으나 **100건 중 25건만 채워져 있다**. 진행상태 판정은 문서 첨부 여부로 하기 때문에 발급일이 비어도 거래완료가 된다 — **`status_entered_at` 을 이 컬럼으로 파생하려는 시도는 실패한다.**

### 회의에서 정할 것 (권고안)

> **ERP는 「B/L 발급」까지 권위 소스로 삼고, 그 이후 tracking(8~11)은 별도 소스로 분리한다.**
> 선택지는 ①포워더 데이터 수집(문서 Q6이 예상한 경로) ②선사 스케줄 조회 ③ERP에 상태 전이 이력을 신설(=추가개발, §7-C).
> 이 선을 먼저 긋지 않으면 매핑 시트를 다 채워도 Phase 2에서 막힌다.

## 4. §2 필드 매핑 시트 — ERP 대응 컬럼 (실측)

> 표기: `테이블.컬럼` / `계산값` = DB 컬럼이 아니라 서버 계산 결과(API가 계산해서 내보냄)

### 4.1 바이어

| 포털 필드 | ERP 대응 | 비고 |
|---|---|---|
| erp_buyer_code | `buyers.id` | **전용 코드 없음.** 접두사 권장(`heymanerp:13`) |
| buyer_name | `buyers.name` | 운영에 앞뒤 공백 오염 **1건** — 매칭 전 TRIM 정규화 필요 |
| country | `buyers.country_id` → `countries.name` | |
| salesperson | `buyers.salesman_id` → `salesmen.name` | |

### 4.2 차량 / 주문

| 포털 필드 | ERP 대응 | 비고 |
|---|---|---|
| erp_buyer_code | `vehicles.buyer_id` | ⚠️ **3개 칸이 있다** — 아래 「바이어 칸 문제」 |
| car_ref | `vehicles.id` | 안정 키. 사람이 보는 번호는 `vehicle_number`(한글 번호판) |
| vin | `vehicles.nice_reg_vin` | ✅ **채움률 239/239 = 100%** (판매차 235/235) |
| make / model / year | `brand` / `model_type` / `year` | NICE 조회 원본은 `nice_spec_*` 에 별도 존재 |
| fob_amount / currency | `sale_price` / `currency` | ⚠️ **FOB 정의 주의** — 아래 「금액 정의」 |
| paid_at | 🔶 **계산값** — `final_payments` 확정분의 `MAX(confirmed_at)` | ⚠️ 정의 위험 — 아래 「paid_at」 |
| status_code | 🔶 **계산값** — `progress_status` | §3 참조 (8~11 불가) |
| status_entered_at | ❌ 없음 | §3 |
| expected_next_at | ❌ 없음 | §3 |
| dest_port | `vehicles.discharge_port_id` → `ports.name` | 판매차 235 중 **121건**만 채움 |
| shipment_ref | ⚠️ **선적 「건」 개념이 없다** | 아래 4.4 |
| photo_ref | `vehicle_photos.path` | 🚨 **PII 위험** — 아래 「사진」 |

#### ⚠️ 바이어 칸 문제 (가장 위험한 항목)

차량에 바이어 칸이 **3개** 있다 — `buyer_id`(판매) / `export_buyer_id`(통관) / `bl_buyer_id`(선적). 어느 걸 "이 바이어의 차"로 볼지 틀리면 **A 바이어가 B 바이어의 차를 본다.**

**실측 (heymanerp 239대)** — 세 칸 모두 실제로 널리 쓰인다:

```
buyer_id(판매) 239 · export_buyer_id(통관) 143 · bl_buyer_id(선적) 148
판매 ↔ 통관 바이어가 다른 차량 = 0건   ← 둘 다 채워진 143건에서 검증
```

지금은 세 칸이 일치하지만, **스코프 기준은 `buyer_id`(판매) 로 고정한다.** 이유:

- 포털 스코프의 의미는 **"누가 청구 대상인가"** 이고 그건 판매 바이어다. 통관·선적 바이어는 "서류상 누구 앞으로 보내는가"라서 콘솔리데이터 등 **제3자가 들어올 수 있다.**
- 참고로 기존 `effective_consignee` 는 **통관 → 선적 → 판매** 순(후행 우선)인데, **이 순서를 바이어에 그대로 복사하면 안 된다.** 그렇게 하면 판매 바이어가 A, 통관 바이어가 B인 차가 생기는 순간 **A가 산 차가 B의 포털에 뜬다.**
- 우리 쪽에 **같은 유형의 사고 이력**이 있다(컨사이니 입력칸을 옮겼는데 읽는 쪽 4곳이 그대로여서 화면이 통째로 빈값). 그래서 **`effective_buyer` 단일 출처를 먼저 정의**하고 스코프를 거기에 거는 것이 이 연동의 **선행 개발 1번**이다 (§7-C).

#### 🚨 금액 정의 — 포털은 「FOB·USD」 전제인데 실거래는 「CFR·EUR」 이다

포털 필드명이 `fob_amount`(FOB = 운임 미포함)이고 SSP 적립도 USD 기준이다. **운영 실측은 정반대다:**

```
인코텀즈 (판매차 235):  CFR 219  ·  미입력 16  ·  FOB 0건        ← FOB 거래가 하나도 없다
통화     (판매차 235):  EUR 190  ·  USD 34   ·  KRW 11          ← 주력이 EUR
운임비 별도 기재:       221건 (transport_fee > 0)
```

즉 포털이 요구하는 값을 만들려면 **두 번의 변환**이 필요하다:

| 변환 | 내용 | 문제 |
|---|---|---|
| ① 인코텀즈 | CFR 총액 → FOB(운임 제외) 로 환산 | `transport_fee` 를 빼면 되지만, **미입력 16건**은 판정 불가 |
| ② 통화 | EUR/KRW → USD | **어느 시점 환율인가** — 판매시점? 입금시점? 조회시점? |

ERP가 관리하는 금액 칸은 여러 개이고, 바이어 청구총액은 다음과 같다:

```
판매총액(CFR) = sale_price + transport_fee(운임) + sale_other_costs + commission + auto_loading − tax_dc
FOB 상당액   = 판매총액 − transport_fee
```

> **회의 결정 필요 2건**: ①포털이 표시할 금액을 **CFR 총액으로 바꿀지**, FOB로 환산할지 (실거래가 CFR이니 **CFR 표시가 자연스럽다** — 바이어가 실제로 내는 돈이다) ②USD 환산 시점 규칙. 환산을 포털이 할지 ERP가 할지도 함께.
> (참고: 수출신고 금액 `export_declaration_amount` 는 또 다른 값이라 이 계산에 쓰지 말 것.)

#### ⚠️ `paid_at` — "없다"가 아니라 "정의가 위험하다"

파생은 가능하다(`final_payments` 277건 전부 확정 상태). 그러나 ERP의 **완납 판정에는 실입금이 아닌 것들이 포함**된다:

- 적립금 사용(크레딧으로 잔금 결제)
- 채권 회수이력 중 **상계(offset)·손실처리(write_off)** — 운영 실측 **2건 존재**

즉 **못 받은 돈을 손실처리해서 완납이 된 차도 `paid_at` 을 얻는다.** 포털 §7이 SSP 적립 트리거를 `paid_at` 으로 잡았으니 → **받지 못한 돈에 바이어 크레딧이 적립**된다.

> 회의 안건: 적립 트리거를 **실입금(현금) 경로로 완납된 경우로 한정**할지. 한정한다면 ERP가 `paid_at` 과 별도로 "실입금 완납 여부" 플래그를 함께 내보내야 한다(§7-C).
> (참고: 판매계약서에 손실처리액을 바이어에게 노출하지 않기로 한 기존 결정과 같은 맥락이다.)

#### 🚨 사진 — 그대로 열면 PII가 나간다

`vehicle_photos` 는 사진 전용이 아니라 **첨부 일반**이다. 운영 실측 확장자 분포:

```
jpg 852 · pdf 71 · png 56
```

**PDF 71건**에는 등록증·서류 스캔이 섞여 있고, 여기엔 **소유자 성명·주소·주민등록번호**가 인쇄돼 있다. 카테고리는 절반이 미분류다(`NULL` 507 / `shipping` 472).

> ⚠️ **확장자 필터(jpg/png 허용)로는 못 막는다** — 직원이 등록증을 **카메라로 찍으면 그게 `.jpg`** 다. 실제로 jpg가 852건이고 그중 다수가 미분류다.
>
> 처리: **명시 카테고리 allowlist(차량 외관 등) + `NULL` 은 기본 거부.** 미분류를 노출하려면 사람이 분류하는 절차를 먼저 둔다. 확장자는 보조 조건일 뿐이다.
> 반환은 저장 경로가 아니라 **요청 시 발급하는 단기 서명 URL**(현재 서류 다운로드가 쓰는 방식과 동일).

### 4.3 인보이스 / 입금

🚨 **ERP에 인보이스 엔티티가 없다.** (`forwarding_invoices` 는 포워더 비용 쪽이라 **매핑하면 안 된다**.)

| 포털 필드 | ERP 대응 | 비고 |
|---|---|---|
| invoice_no | 🔶 **문서 생성 시점에 계산** | ⚠️ 안정 키 아님 — 아래 |
| erp_buyer_code | `vehicles.buyer_id` | |
| issued_at | ❌ 없음 (발행 개념 없음) | |
| due_at | ❌ 없음 (결제 마감일 칸 없음) | |

인보이스 번호는 「영업 이니셜 + 차대번호 끝자리」로 **문서를 만들 때 즉석 계산**된다. 이니셜이 없으면 **생성 시점의 연월**이 들어가는 대체 규칙이라, **같은 차도 달이 바뀌면 번호가 달라진다.** 미러 키로 쓸 수 없다.

> **권고: 청구 단위를 「차량 1대 = 인보이스 1건」으로 합성**하고, 키는 `vehicles.id` 를 쓴다(`car_refs` 는 항상 1원소). 여러 대를 묶은 실제 인보이스 엔티티를 ERP에 신설하는 건 **별건 개발**이다(규모 §7-C).

## 6. 스코프 — 이 연동의 핵심 설계 (포털측이 알아야 할 것)

기존 board API는 **「영업 본인」** 축으로 격리한다(영업 이메일 → 그 영업의 차만). 바이어 포털은 **「바이어」** 축이 필요하다 — **완전히 다른 축이라 기존 엔드포인트를 재사용할 수 없다.**

신설 원칙:

- **별도 시크릿 · 별도 rate limit 키 · 별도 스코프 클래스** (board와 공유 금지)
- 호출 시 **바이어 식별자를 서명에 포함** → 위조 차단
- 서버가 `effective_buyer` 기준으로 **강제 필터** (호출자가 범위를 넓힐 수 없음)
- 응답 화이트리스트는 board보다 **더 좁게** — 바이어는 외부인이다:
  - ⛔ 매입가·비용·마진·정산 (**바이어가 우리 원가를 보면 안 된다**)
  - ⛔ RRN·소유자명/주소·계좌·영업 개인정보
  - ✅ 자기 차량·자기 청구·자기 선적·자기 서류만
