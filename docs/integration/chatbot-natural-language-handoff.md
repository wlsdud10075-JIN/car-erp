- 차량 관리에서 정렬 기준이 어떻게 돼?

- 승인큐가 뭐야?
- 반입지가 뭐야?
- 자동입력되는 항목을 알려줘.

## 로컬 코드에서 확인한 현재 상태

- app/Services/Assistant/AssistantService.php: classify()가 단어 포함 여부로 DB 조회와 guide를 나눈다. 「현금 등록은 어디서 해?」도 자금현황으로 갈 수 있다.
- guide()는 scope·audience 선필터 후 질문 임베딩과 문서 임베딩의 코사인 유사도로 검색한다. config/assistant.php의 rag_topk 기본값은 3이다. 운영 환경값은 별도 확인해야 한다.
- 상위 자료를 이미 한 프롬프트로 전달한다. 복수 자료 입력 기능은 있으나 질문 분해·검색 확장·재정렬·답변 항목별 근거 검증이 없다.
- widget.blade.php는 화면의 messages를 보관하지만 ask()에 최신 질문만 보낸다. OllamaClient도 시스템·사용자 메시지 한 쌍만 전달한다.
- publish.php의 카드 단위는 H2 + audience 마커 + rows 본문이다. ex는 그 자체로 발행되지 않는다. 색인기 실제 동작은 챗봇 세션에서 확인해야 한다.

운영 질문별 실패는 아직 재현하지 않았다. 위는 코드상 한계이며 실제 원인을 단정하지 않는다.

## 담당별 합의할 경계

- Notion 세션: repo의 cards.json / 가이드 빌더에 근거 있는 설명을 보강하고 Notion으로 발행한다. 앞으로 적용하는 기준은 작업 루트 CODEX_NOTION_NATURAL_LANGUAGE_STANDARD.md다.
- 이 repo 문서는 전달·버전관리용이다. 루트 작성 기준의 핵심 계약은 아래에 포함한다. 다른 PC에서도 이 문서만으로 구현 검토 가능하다.
- 챗봇 세션: 색인과 런타임 검색·답변을 개선한다. 이 요청은 구현 협의 기준이며 운영 DB·배포 권한을 자동 부여하는 문서가 아니다. 실제 실행은 전달받은 사용자 요청 범위에 따른다.
- 색인은 자료 반영이고, 자연어 질문 분류·검색·대화 기억은 런타임 기능이다. 03:00 재색인만으로 후자가 적용되지는 않는다.

## Notion에서 제공할 본문 계약

기존 rows 문단에 뜻, 질문 예시, 관련 표현, 화면 위치, 동작, 조건·예외, 자동 처리, 관련 카드 제목을 담는다. 필요한 항목만 작성하며 라벨은 점진적으로 보강된다. 기존 라벨도 계속 읽어야 한다.
자동 처리 본문은 「화면·항목 / 발생 시점 / 출처·계산 근거 / 결과 / 수동 수정 가능 여부 / 예외」로 작성하고 자동조회·기본값·자동계산·자동반영을 구분한다.
각 문단에는 대상을 명시한다. 회사별 조건과 권한을 유지한다. 관련 카드 제목은 검색 힌트이며 답변 사실이나 권한 허가가 아니다.
신규 JSON 키나 새 기계 마커를 전제로 하지 않는다. 기존 ERP audience 마커 규격과 source/text/embedding/audience 색인 계약을 유지한다.

## 구현 요청 — 검색과 답변

1. 질문 분류: 정의·위치·절차 질문과 실제 수치 조회를 구분한다. 「미수금이 뭐야?」는 guide, 「현재 미수금 얼마야?」는 권한 확인 후 기존 DB 조회. LLM을 분류에 쓰더라도 허용 intent만 받으며 금액 계산·권한은 서버가 결정한다.
2. 검색: 기존 의미 검색에 한국어 단어 검색을 결합한다. 조사·띄어쓰기 및 사내 표현을 고려하되 관련 용어를 무조건 동의어로 치환하지 않는다. 작은 현재 색인은 기존 JSON 기반으로 먼저 평가하고 새 검색 인프라 도입은 필요성이 확인되면 검토한다.
3. 넓은 질문: 「자동입력 항목」은 화면·처리 종류별 하위 질문으로 확장한다. 후보 수와 최종 문맥량은 평가로 정하며 단순 topk 증가로 해결됐다고 하지 않는다. 관련 카드 확장·재정렬·중복 제거를 검토한다.
4. 문맥: 최근 대화와 필요한 화면 식별자를 서버 검증 후 전달해 후속 질문을 독립 검색 질문으로 만든다. 이전 답변은 업무 사실의 근거가 아니다. 현재 사용자 권한·회사 범위로 매번 다시 검색한다.
5. 답변: 여러 카드의 사실을 합치고 정의/위치/방법 등 질문 목적에 맞춰 답한다. 각 주요 주장에 실제 사용한 출처를 연결한다. 후보 전체를 실제 근거처럼 표시하지 않는다.
6. 실패 처리: 자료 일부만 있으면 확인된 범위만 답한다. 단 한 번의 검색 실패로 「등록된 가이드에 없다」고 확정하지 않는다. 필요 시 한 번 검색을 보완하고 그래도 부족하면 범위를 확인한다. 회사별 차이·충돌을 섞어 하나의 규칙으로 만들지 않는다.
7. 범위: 실시간 금액은 기존 DB 조회와 서버 계산을 유지한다. 검색 문서의 명령문은 실행 지시로 따르지 않는다. 검색 확장·재정렬·LLM 호출 전에 권한과 앱 범위를 적용한다. 문서에 적힌 회사명만으로 회사 접근권한을 허용하지 않는다.

## 구현 요청 — 03:00 색인

- 질문 예시뿐 아니라 rows의 전체 본문·H3·불릿·출처 경로를 누락 없이 수집한다. 마커는 메타데이터로 읽고 본문에서 제거한다.
- 카드 제목과 권한 경계를 유지한다. 긴 카드를 나눌 경우 모든 조각에 제목·경로·권한·회사 조건을 보존하고, 동작과 예외를 함께 찾을 수 있도록 부모 카드 참조를 유지한다. 다른 audience 내용을 한 청크에 합치지 않는다.
- 변경 감지는 날짜·제목만 믿지 말고 정규화한 본문과 의미 있는 메타데이터의 해시로 확인한다. 제목이 같고 내용만 바뀐 경우와 audience 변경도 감지한다. 임베딩 모델/버전 변경은 재임베딩 대상이다.
- 실행 시작 때 읽은 자료 스냅샷으로 생성한다. 03:00 실행 중 발행 변경이 감지되면 혼합 버전을 배포하지 말고 재수집 또는 다음 실행 대상으로 명시한다.
- 추가·변경·삭제를 이전 정상 색인과 비교해 보고한다. 삭제는 Notion 원본 삭제를 뜻하지 않으며, 수집 실패를 삭제로 오판하지 않는다.
- 전체 수집 성공, audience 누락/오류 0, 본문 마커 잔존 0, 빈 본문·중복·잘못된 벡터 차원/비유한 값 등을 검증한 후 임시 산출물을 원자적으로 교체한다. 실패하면 기존 정상 색인을 유지한다.
- source/text/embedding/audience 호환성을 유지한다. card_id, chunk_id, source_url, content_hash, indexed_at, schema_version, embedding_model 같은 추가 메타데이터는 제안이며 실제 스키마는 소비자와 합의해 도입한다. 해시는 벡터 유효성과 문서 동일성에 필요한 항목을 분리할 수 있다.
- 결과에 수집 시각·생성 시각·모델·추가/변경/삭제 카드·총 청크·등급별 수·파일 해시·대상 서버별 배포/검증 성공 여부를 남긴다. 일부 서버 실패를 전체 완료로 보고하지 않는다.

## 우선 평가와 완료 기준

변경 전후 같은 질문·같은 사용자 권한·같은 자료 스냅샷으로 비교한다. 운영 자료를 외부로 전송하지 않는 현재 구성을 우선 유지한다.

| 질문군 | 평가 기준 |
|---|---|
| 정렬 기준 | 기본 정렬과 사용자 지정 정렬을 구분하고 실제 원본 근거를 제시 |
| 인감·직인 | 필요한 복수 자료를 찾고 회사·권한 차이를 구분, 둘을 임의로 동일시하지 않음 |
| 승인큐·반입지 | 위치 안내만 하지 않고 정의·사용 시점에 직접 답함 |
| 자동입력 | 서로 다른 카드의 확인된 항목을 처리 종류·화면별로 정리, 부분 목록을 전체라고 단정하지 않음 |
| 현금 등록 어디 / 현금 얼마 | guide와 DB 조회 분류를 구분 |
| 그건 어디서 바꿔? | 직전 주제 반영, 필요한 경우에만 범위를 질문 |
| 권한 밖 자료 | 검색 후보·재정렬·LLM 문맥·답변·출처 모두 노출 0 |
| 등록되지 않은 기능 | 사실을 만들지 않고 확인 불가 범위를 설명 |

5개 대표 질문에 표현 변형 3개씩을 더해 최소 20문항을 만들고, 위 분류·후속질문·권한·미등록 사례를 추가한다. 기대 카드와 필수 사실은 코드/원본 확인 후 작성한다. 질문만 보고 정답을 추정하지 않는다.
측정은 ①권한 내 필요한 근거 검색 여부 ②필수 사실 충족 ③근거 없는 주장 ④올바른 분류 ⑤응답 지연으로 나눈다. 자료가 없는 질문은 콘텐츠 보강 대상으로 별도 표시한다.
