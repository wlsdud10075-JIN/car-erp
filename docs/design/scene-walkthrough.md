# 씬 워크스루 (Scene Walkthrough) — 기능 1개의 실제 흐름을 「루프 테스트 → 한 장 HTML」로 남기는 표준

> jin 2026-11-12: «이거 잘 이용하면 굉장히 좋을 것 같아». board 세션이 탁송 배차 기능으로 먼저 만든 방식을 **board·ERP 전 기능의 표준**으로 두려 한다(게시처 = Notion 업무가이드 또는 티스토리 + Notion 링크, 결정 = jin).
> 정본 기획 = board 레포 `meetings/plan-scene-walkthrough-2026-11.md`(ERP 후보 씬 §4). 샘플 = board 레포 `mockups/transport-flow-2026-11-12.html`(+ `mockups/transport-flow/*.png`, board dev e28c9a7) — 브라우저로 열어 볼 것. ⚠️ 샘플 본문은 **개발자 초판**이라 아래 「jin 규칙」 2번은 샘플을 따라 하지 말 것.

## 1. 무엇인가

기능 1개의 실제 씬을 **처음부터 끝까지 루프 테스트**(로컬에서 실제로 눌러서 돌린다)로 돌린 뒤, 결과를 **스윔레인 흐름도 HTML 한 장**으로 남긴다.

- **왼쪽 레인 = 누가/어디서**: 영업(board) · 알림톡 · 외부(업체/바이어) · ERP.
- **오른쪽 카드 = 그 단계에서 실제로 보이는 것**. 카드 안에 다섯 가지:
  1. 실제 화면 캡처(헤드리스 스크린샷)
  2. 오가는 알림톡 본문(승인본 그대로 + 실제 값 치환. 로컬 미발송이면 「운영에선 이렇게 간다」로 표기)
  3. API 요청/응답 실측값
  4. 감사 행
  5. 「운영 전 체크」 절(승인·배포 순서·토글 등 남은 것)
- 목적 = **「누가 봐도 쓸 수 있는 사용법」 + 배포 전 씬 검증 기록**. 두 역할을 한 장이 한다.

## 2. jin 규칙 (11-12, 이후 씬 공통)

1. 씬은 **실측**으로만 쓴다 — 숫자·시각은 실제 돌린 값, 스크린샷은 그 실행의 것. 예상값은 「운영에선 이렇게 간다」로 구분 표기.
2. **사용자용 본문에는 변수명·엔드포인트·상태코드를 쓰지 않는다.** 「어느 화면에서 무엇을 누르면 무엇이 보인다」로만 쓴다. 개발 상세(API·JSON·감사 컬럼명)는 **접힌 블록**(`<details>`)에만.
3. 수신자·라우팅처럼 **회사별 설정값**에 달린 문장은 「어느 회사 · 언제 실측」을 카드에 단다(코드 기본값과 설정값이 다를 수 있다 — 11-12 7번 알림톡 수신자 문구에서 확인).
4. 전화번호 원문·계좌·주민번호는 캡처·본문에 넣지 않는다(마스킹 그대로).

## 3. 만드는 법 (ERP 쪽)

- 화면 캡처 = 헤드리스 크롬. ERP 세션엔 `playwright-core` + 설치된 Chrome 스크립트가 있다(세션 scratchpad `pw/` — 로그인 `admin@car-erp.test`, 로컬 8001, 390px 모바일 컨텍스트 예시 포함). 레포에 둘 땐 `scripts/scene/`(dev 전용, master 제외)로.
- API 실측 = PHP 부트스트랩 스크립트로 서비스·컨트롤러를 직접 호출해 JSON 기록(`php artisan tinker` 는 멈춘다 — `reference_local_tinker_hangs`).
- HTML 은 네 가지 스타일만: 레인 · 카드 · 카톡 말풍선 · 코드 블록. 샘플 HTML 의 CSS 를 그대로 가져다 쓴다.
- 알림톡 본문 = `AlimtalkTemplates::TEMPLATES` 의 승인본 + 실제 vars 치환(조립 규칙은 그 커맨드/컨트롤러 그대로 — 손으로 다시 쓰지 말 것, 11-12 7번처럼 줄 순서가 어긋난다).

## 5. 흡수 금지
- 🚫 샘플 HTML 을 ERP 레포에 복사하지 않는다 — CSS·틀만 가져오고 씬 내용은 ERP 실측으로.
- 🚫 씬 문서를 스펙 권위로 쓰지 않는다 — 스펙은 종전 권위 문서(`board-portal-api.md`·`purchase-sync-receiver.md` 등), 씬은 **그 스펙이 실제로 어떻게 보이는가**의 기록.
