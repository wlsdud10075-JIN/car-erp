## 3. 결정을 가르는 제약 — 우리 규칙

우리 작업 규약은 **main 이 단독 write · 서브에이전트는 조사만 · master push 는 매건 jin 승인 · 운영 SSH 읽기전용 · master 1회 = 3사 동시배포**다.
「가상 회사」류(claw-empire·connect-ai)의 기본값은 **CEO 지시 → 자동 배정 → 자동 브랜치 → 머지 → 레벨업**이라 정반대다.
⇒ 도입하려면 **읽기·조사·초안 모드로만** 돌리거나, 그 게이트를 다시 구현해야 한다.
⇒ 그래서 **「보는 층」만 공짜**고, 「시키는 층」은 비용이 있다.

### 7-1. 그 기계가 무엇인가 (Apple KR 스펙 페이지 실측 09-28)
- 현재 라인업에서 **32GB 는 M6(기본 칩) 만** 고를 수 있다(대역폭 153~170GB/s). M5 Pro 는 24/48/64GB 라 32GB 가 없고 대역폭 307GB/s.
- 뜻: **로컬 LLM 속도는 GB 가 아니라 대역폭이 정한다.** 32GB M6 은 「8~14B 모델은 넉넉히, 27~30B(Q4)는 들어가지만 느리다」 급. 우리 챗봇 쌍(qwen3:8b + bge-m3, 약 6GB)은 여유가 크다.
- 대기 전력 몇 W, 소음 없음 → **24시간 켜 두는 기계**로 적합. Tailscale 에 넣으면 3사 서버·이 PC 와 같은 망.

#### 3. BOARD→ERP 전송 누락의 상태값과 SQL 기준

**board 코드에서 확인했다.** 상태 의미는 다음과 같다.

- 전송 시작 대상: `purchase_listings.status='won'` — 상태가 `won`으로 바뀌면 Job을 큐잉
  (`board/app/Models/PurchaseListing.php:401-406`).
- 전송 완료: ERP가 2xx와 `vehicle_id`를 반환한 뒤 **`car_erp_vehicle_id`를 저장하고 `won→synced` 전이**
  (`board/app/Jobs/SyncWonListingToCarErp.php:234-247`).
- 따라서 board 쪽 완료 기준은 **`status='synced' AND car_erp_vehicle_id IS NOT NULL`**이다.
- Job은 5회, 1·5·15·30분 간격으로 재시도한다(`SyncWonListingToCarErp.php:28,44-47`). 그래서 즉시 `won`을
  누락으로 세지 않고 **60분 이상 정체**를 1차 후보로 잡는다.

board DB의 1차 카운트 SQL:

```sql
SELECT COUNT(*) AS stalled_purchase_sync_count
FROM purchase_listings
WHERE deleted_at IS NULL
  AND status = 'won'
  AND car_erp_vehicle_id IS NULL
  AND updated_at < NOW() - INTERVAL 60 MINUTE;
```

상세 목록은 같은 조건으로 `id, vehicle_number, updated_at`을 뽑고, `integration_events`에서
`direction='outbound' AND target='car_erp' AND event_type='purchase_sync' AND purchase_listing_id=id`의 최신 행을
붙여 `response_status`, `error`, `created_at`을 보고한다. 로그 컬럼 근거는
`board/database/migrations/2026_06_15_000001_create_integration_events_table.php:16-29`, 실제 기록은
`SyncWonListingToCarErp.php:223-232`다.

정합성 오류도 별도 집계한다.

```sql
SELECT
  SUM(status = 'synced' AND car_erp_vehicle_id IS NULL) AS synced_without_erp_id,
  SUM(status <> 'synced' AND car_erp_vehicle_id IS NOT NULL) AS erp_id_without_synced
FROM purchase_listings
WHERE deleted_at IS NULL;
```

단, 첫 SQL은 정확히는 **「board에서 ERP 전환이 완료되지 않은 정체 후보」**다. ERP가 생성 응답을 보냈는데 board가
응답 직후 죽은 극단적인 경우에는 ERP에 차량이 있어도 여기에 잡힐 수 있다. 진짜 「BOARD에는 완료인데 ERP에는 없음」은
board의 `synced + car_erp_vehicle_id` 집합을 ERP 읽기 API의 차량 ID/차량번호 집합과 대조한 **집합 차이**로만 확정한다.
별도 DB끼리 직접 JOIN하거나 한쪽 DB 자격증명을 다른 앱에 주지 않는다.

### 13-2. 작업 큐(agent_tasks 장부 + 텔레그램 명령 → Codex 실행 → 결과 회수) — **지금은 안 만든다.**
- 이건 jin 이 09-28 낮에 뺀 **원격 명령·상시 세션 층(#2·#3)** 이다. 첫 성공 기준(「텔레그램에서 Codex 에게 조사시켜」)은 회사 PC 에 **봇 폴링 프로세스 + 작업 실행기**를 새로 두는 것이고, `codex queue` 는 **살아 있는 Codex 창**이 있어야 받는다 — 「밤엔 세션 없음」과 모순.
- Codex 자신도 적었다: 구독 CLI 는 로그인 만료·한도·업데이트로 멈추니 **무인 필수 운영엔 못 쓴다**. 그러면 큐의 소비자가 불안정한데 장부만 정확한 상태가 된다.
- 지금 실제 흐름(jin → 창에 직접 · 낮 · 승인 즉시)에서 장부는 **의식(儀式)만 늘린다.** 기록은 이미 세 곳에 있다: 야간 보고 파일 · 메모리 · 이 문서/커밋.
- 🔁 **되살릴 조건**: 2~3주 뒤 jin 이 「폰에서 Codex/Claude 에 일감을 던지고 싶다」가 실제로 반복되면. 그때의 최소 형태 = JSON 장부 1개 + `codex exec`(헤드리스) 실행기 + 결과 JSON. 그 전엔 안 한다.

### 13-3. 가져올 것 둘 (작게)
- **결과 회수 형식** — 야간 보고 파일 머리에 고정 JSON 3줄(`date · counts{이상 N} · needs_decision[]`)을 붙여 두면 나중에 무엇이든(텔레그램 요약·주간 통계) 그걸 읽는다. 03:30 스크립트 prompt 에 한 줄 추가로 끝. 텔레그램 ON 할 때 같이.
- **권한 4단계 어휘** — read_only / workspace_write / external_write / production. 우리 규칙과 같다(조사·초안 = read_only 자동, dev 커밋 = jin 이 시킨 것, 텔레그램·Notion = 별도, 운영·배포 = 매건 승인). §11-2 의 말로 채택.

### 13-4. 결론
Codex 의 그림에서 **텔레그램 부분은 이미 우리 것이고, 큐 부분은 jin 이 뺀 층**이다. 남은 실제 빈칸은 「ssancar.com 미러 최신성 1행」과 「야간 보고 JSON 머리 3줄」뿐. 둘 다 작다.
