## 4. 분류 설계

**유형** = 요청 / 질문 / 대답 / 확인(네·넵·감사) / 정보(일정·금액·링크) / 잡담 / 첨부(사진·파일·이모티콘, 분류 제외).
**방향** = 상대→나(내가 할 일) / 나→상대(기다리는 것) / 나와 무관(내가 수신자·발신자가 아닌 것 — 단체방).

**1단계 = 규칙(2번) + 임베딩 분류기(3번)**
- 규칙 = 글자 패턴. 이 회사 실무자는 반쯤 정해진 서식을 쓴다 — 「매입액 : … / 바이어 : … / 계약금: N만원 입금 부탁드립니다」(계약금 송금 요청 + 금액·바이어 추출), 「~부탁드립니다/승인 부탁」=요청, 「~요?/~까요?」=질문, 「넵/알겠습니다/감사합니다」=확인, 「사진/파일: *.pdf」=첨부, 「@이름」=대상, 차량번호 `NN가NNNN` = 어느 차. 한계 = 「배차하셔도 됩니다」(허락), 완곡 요청, 그리고 **해결 연결**은 규칙으로 거의 안 됨.
- 임베딩 분류기 = 문장 → 벡터(bge-m3, CPU 가능·0.7GB) → 작은 분류기(수 MB)로 유형. **학습 데이터 = 무사백-수출팀 내보내기 20,546건**(jin 바탕화면 `KakaoTalk_20261109_1503_03_399_group.txt`, 2025-08-29~2026-11-09) 중 300~500건 라벨(Claude 가 달고 jin/팀장 표본 검수). 장점 = 사내·무료·실시간·우리 말투에 맞춤·수정이 학습이 됨. 한계 = 유형 고르기만(요약·해결 연결·값 추출 ✗), 라벨 필요, 정확도 85~90% 선.
- 「해결됐나」 = 규칙(같은 차량번호·금액의 후속, 요청 뒤 상대의 확인/완료 보고) + 사람이 최종(주 버튼). 자동 판정은 「아마 해결」 표시만.
- 2단계(선택) = 요약·맥락 경고(영상의 「조립 전 중지!」)가 필요해지면 LLM 하나를 붙인다 — ~~11-09 결정(§1 #13): 사내 16GB PC + Qwen3 14B~~ → ✅ **11-10 (§1 #14): Claude API(대표 개인 PC 경유).** 그러면 1단계 라벨링·임베딩 분류기는 **일단 건너뛴다** — API 가 분류·연결·추출을 한 번에 한다. 실무자 PC 의 규칙은 첨부·잡담 제거 + 전화·계좌 마스킹(토큰·노출 절감)으로 남긴다. 월 비용·노출·속도가 문제 되면 그때 OCR PC 의 bge-m3 임베딩 분류기를 앞단에 붙인다(혼합).
- **프롬프트 확정 규칙(11-10, 표본 2개 실측)**: (a) 앞 요청·질문에 이어지는 응답은 사실 전달이어도 「대답」, resolves 에 그 id (b) 공백 없는 6자리 숫자(131538)는 차대번호 끝자리 = `vin_tail`, 금액 아님 (c) 완료 보고에 「확인 부탁/이상 유무 알려주세요」가 붙으면 「요청」(상대 할 일) (d) §1 #15 의 6규칙. 출력 스키마 = type·to·mention·ref(컨테이너/BL)·vehicle·vin_tail·amount·resolves. 방 구성(누가 어느 편인지)은 방마다 설정으로 주입. 그 분류기의 **학습 라벨은 API 분류 결과로 만든다**(증류, jin 11-10) — 첫날부터 API 출력을 메시지 키별로 저장해 두면 라벨 작업이 따로 없다.

## 5. 화면 사양 (v4 목업 = 정본)

- 창 하나(폭 ~700px). 제목 「내 카톡 할 일」 · 상태 한 줄 「HH:MM 읽음 · 최근 7일 · 방A 외 N곳 · 방 선택」 · 노란 **[지금 읽기]**. 뜻 못 정한 메시지가 1건이라도 있으면 바로 아래 경고줄 「확인 필요 N — 지금 정하기」.
- 묶음(기본 전부 접힘, 제목 = 건수 + 이름 + 한 줄 뜻 + 「펼치기/접기」):
  1. **놓쳤을 가능성**(연한 빨강) — 마감·재확인 시점 지남 / 「넵」만 하고 처리 확인 없음 / ERP 에 연관 기록 없음 / 며칠째 상태 변화 없음. 확정이 아니라 가능성 → 확인을 청한다.
  2. **지금 할 일** — 들어가는 조건은 **이유**(다른 사람·돈이 막힘 / 시간 민감 / 오늘 마감 / 놓치면 손실). 경과시간만으로는 안 올린다.
  3. **오늘 안에** — 막힌 사람 없음, 단순 전달, 준비물 부족.
  4. **답 기다리는 중** — 내가 상대에게. 각 요청에 「HH:MM까지 기다림」. 지나면 1 로 승격.
  5. **미뤄둔 일** — 「언제까지 미룸 · 사유」. 시점이 오면 2 로 올라온다.
  6~8. 접힘: 오늘 끝난 것(자동 완료 후보 표시) · 확인 필요 · 나와 무관.
- 행 = 동사형 제목 · 누가↔누구 · 시각·방 · 마감/재확인 시점 · **지금 보여주는 이유(알약 1개)** · 핵심값(차량번호·금액, 추출된 것만) · 버튼 **[주 버튼][미루기][⋯]**(차량번호 확실하면 [차량 열기] 추가). 행 본문을 누르면 원문·앞뒤 대화 + [ERP 확인][분류 수정][내 일이 아님].
- [⋯] 목록 = 보기(원문 펼치기 · 카톡에서 이 방 열기) / 처리(지금 재촉=문구 복사 · 내 할 일로 전환 · 차량 열기 · ERP 확인) / 분류(분류 수정 · 내 일이 아님) / 무시.
- 미루기 팝오버 = 오늘 오후 16:00 / 내일 오전 10:00 / 날짜 지정 / 상대가 답하면 / ERP 상태가 바뀌면 + 사유.
- 뺀 것(관리자 분석 화면으로 보냄): 인원 칩 · 요약 카드 · 유형/금액/확신 뱃지 상시 노출 · 아바타 · 엑셀 · 학습 설명 · 메시지 총 개수.
- 제안(미결): 「놓쳤을 가능성」만 건수 ≥1 이면 자동 펼침.

## 6. 동작 설계 (A안)

- 트레이 상주 프로그램(윈도우). 저장 = 로컬 상태 파일/SQLite — 메시지 키(방·보낸이·시각·본문 해시)별 **유형 · 방향 · 상태(할 일/기다림/미룸/완료/무시) · 다시 볼 시각 · 사유**. 그래서 다시 읽어도 새로 안 뜨고 완료·미룸이 유지된다.
- [지금 읽기] = 체크한 방을 차례로: 목록 더블클릭으로 열기 → 빈 여백 클릭 → 마지막 읽은 시각까지 PageUp(처음은 7일) → Ctrl+A·C → 파싱 → **클립보드 원복** → 다음 방. 방당 1~2초, 진행 중엔 사용자가 손 떼야 함(안내 문구).
- 미루기 시각 = 트레이가 그 시각에 올리고 뱃지. PC 꺼져 있었으면 다음 실행 때 「미룬 시점 지남」→ 놓쳤을 가능성. 조건형(상대 답·ERP 상태)은 다음 [지금 읽기] 때 판정(ERP 는 선택적으로 15분마다 가볍게 확인 가능 — 카톡은 안 건드림).
- 분류 수정 1건 = 라벨 1건 → 주 1회 재학습(로컬).
- B 단계(나중): 결과를 ERP `board_requests` 와 같은 모델로 올려 매입 탭·채권관리와 연결, PC 바꿔도 이력 유지. 개인 대화 서버 저장 → 직원 동의 필요.

## 10. ERP 구현 설계 (2026-11-10, #14·#15 뒤 — 코드 착수 기준)

**원칙**: A안(개인 PC 저장)은 폐기하고 **B 단계로 바로** — 수집만 각자 PC, 분류·저장·화면은 ERP. 3사 공통 코드, 회사별 토글(super 기능설정, 기본 OFF), 키는 각 서버 `.env`.

### 10-1. 흐름
```
실무자 PC 수집기(트레이, [지금 읽기]) ─Ctrl+A·C─▶ 파싱(날짜/시각/보낸이/본문, 여러 줄 병합)
   ─POST /api/kakao/ingest (사용자 토큰)─▶ ERP: 방·메시지 저장(중복 제거: 방+날짜+시각+보낸이+본문 해시)
   ─▶ 새 메시지 + 그 방의 열린 항목 ─▶ Anthropic Sonnet 5.5 (구조화 출력, 시스템 프롬프트 캐시) ─▶ 판정 저장
   ─▶ 그 방을 구독한 사용자마다 방향(내 일·기다림·동료·무관) 계산 ─▶ 「내 카톡 할 일」 페이지(Volt)
```
- **분류는 방 단위 1회**(#15 실증). 같은 방을 두 사람이 읽어도 두 번째 읽기는 새 메시지만 분류한다.
- 방향은 저장하지 않고 보는 사람 기준으로 계산(보낸이·to·mention·방 구성). 사용자 상태(완료·미룸·내 일 아님)만 저장.

### 10-2. 테이블 (마이그 1개)
| 표 | 칸 | 비고 |
|---|---|---|
| `kakao_rooms` | id, name(방 제목, 회사 안 유일), sides JSON(편 구성: `{"재무":[이름…],"수출팀":[…],"영업":[…]}` + 역할 설명), last_read_at | 방 설정은 페이지에서 사용자가 한 번 적는다(프롬프트의 「방 구성」) |
| `kakao_room_users` | room_id, user_id, my_name(그 방에서 나의 카톡 표시명), created_at | 구독 = 체크한 방 |
| `kakao_messages` | room_id, msg_key(sha1), sent_at, sender, body, type, to_side, mention, ref, vehicle_no, vin_tail, amount, resolves_id(FK self), vehicle_id(FK vehicles, 매칭되면), ai JSON(원 판정), created_at | unique(room_id, msg_key). 본문 저장 = jin 「사내방이라 OK」 |
| `kakao_items` | message_id, user_id, state(`todo`/`waiting`/`snoozed`/`done`/`ignored`/`not_mine`), type_override, snooze_until, snooze_reason, done_at | unique(message_id,user_id). 사용자가 건드린 것만 행이 생긴다(없으면 계산값 그대로) |
| `kakao_reads` | room_id, user_id, started_at, finished_at, total, new_count, model, input_tokens, cache_read_tokens, output_tokens, cost_krw, status, error | 비용·사용량 기록(API 키 공용이라 ERP 가 사람별로 센다) |
| `kakao_collector_tokens` | user_id, token_hash(sha256), device_name, last_used_at, revoked_at | 기기별 폐기. users 표에 안 두는 이유 = User 감사 훅이 매 사용마다 울리지 않게 |

🔑 **키·id 결정(11-10, 1단계 뒤 검토)** — 다음 세션이 다시 틀리게 도출하지 않도록:
- `msg_key` = sha1(시각|보낸이|**첫 줄**|같은 (시각·보낸이·첫 줄) 묶음 안 **순번**). 본문 전체를 안 넣는 이유 = Ctrl+A·C 는 화면에 풀린 만큼만 잡혀 긴 서식의 이어지는 줄이 다음 읽기에 더 붙는다(같은 메시지 2번 분류·과금 방지). 순번 = 같은 분에 같은 사람의 「사진」 2개. 적재는 더 긴 본문을 **갱신**으로 받는다.
- 프롬프트의 메시지 id = **`kakao_messages.id`(DB id) 그대로**(1..N 창 번호 ✗). 새 메시지를 먼저 insert(type null) → 창 텍스트 `id=<db id>` + 앞 읽기의 열린 항목도 같은 체계 → 모델의 `resolves` 가 곧 DB id. 검증 = 같은 방·더 이른 sent_at 아니면 null.
- 첨부·스페이서는 모델에 안 보낸다(`isAttachment` → `type='첨부'`), 창에는 `[id=…] (사진)` 한 줄 표식만(흐름 유지, 토큰 절반).
- 방 구성(`sides`) 한 곳에서 프롬프트 「방 구성」 블록과 스키마 `to` enum 을 같이 만든다(어긋나면 400).
- 비용 상한 = 읽기당 새 메시지 `Setting kakao_max_new_per_read`(기본 500, 초과 = 거부·「범위를 좁히세요」) · 사용자당 하루 `kakao_daily_cost_cap_krw`(기본 2,000원).
- `kakao_messages.sent_at` 은 dateTime(카톡 벽시계 그대로), `kakao_reads.*_at` 은 timestamp — 둘을 직접 비교하지 않는다.
- **방 잠금**: 적재는 `Cache::lock('kakao:room:{id}')` 안에서 — 같은 방을 두 사람이 몇 초 사이에 읽어도 분류 1회·유니크 위반 0.
- **방은 페이지에서 미리 등록**(편 구성 + 내 표시명). 수집기가 모르는 방 이름을 보내면 404, 구독 안 한 방은 403 — 빈 구성으로 자동 생성하면 to enum 이 「없음」뿐이라 분류가 조용히 무의미해진다.
- 캐시 실측(11-10): 시스템 프롬프트 ≈2.9k 토큰이 두 번째 호출부터 적중(`cache_read` 2,888). 첫 호출은 캐시 생성(1.25배)으로 `cache_write_tokens` 에 기록·과금.

### 11-1. 사용자가 겪는 흐름

- 에이전트 업데이트: 에이전트가 기동 때 ERP 의 버전을 보고 다르면 새 exe 를 받아 교체(자기 재실행).

2. **차량 상태 카드** — 매칭된 차마다 ERP 사실을 한 줄로: 진행단계 · 매입 미지급(완납이면 「매입완납」) · 판매 미수(통화·완납 여부 = `sale_unpaid_amount` ≤ 0) · 말소 체크/서류 · 선적 4칸(포워딩사·VSL·선적일·ETA) 중 **빈 칸 이름** · 신고서/면장 · B/L. 할 일 행 아래 「ERP: 매입완납 · 말소 미처리 · 선적 칸 비어 있음(VSL·ETA·선적일)」. 전부 기존 accessor(progress_status·purchase_unpaid_amount·sale_unpaid_amount)라 계산 추가 없음. 반나절.
3. **분야·완료 판정에 ERP 쓰기** — (a) 분야 자동: 말소 = 등록 + 매입완납 + 말소 전 / 입금 = 판매 미수 > 0 / 선적 = 판매완납 + 선적 칸 부족 / 통관 = 반입지·신고서 단계. 모델의 `topic` 과 ERP 판정이 다르면 ERP 우선(사실이니까), 둘 다 없으면 「분류 설정 필요」. (b) **ERP 가 처리됐다고 보이면 자동 완료 후보** — 「말소증 부탁」인데 메시지 뒤에 말소서류가 올라옴 / 「계약금 부탁」인데 매입 지급이 찍힘 / 「서렌더 부탁」인데 B/L 올라옴 → 「오늘 끝난 것 · ERP 처리됨」. 메시지 시각보다 **뒤에** 생긴 ERP 변화만 센다(감사로그·updated_at). 하루.
- 🚫 ERP 가 모르는 것(보험·서류 발송·운임 견적)은 모델 분류 그대로 — ERP 연동은 「확인 가능한 것」에만.
- 리액션(13-2)은 별개·보류(한 방만 쓰는 씬이라 전 방 적용 여지 부족 — jin). 로컬 시연은 원하면.
- jin 확인 필요: ①「판매완료」 판정 기준 = 미수 0(소수점 스냅 포함)으로 할지, 입금률 % 를 같이 보여줄지 ②여러 대 메시지의 카드는 대수 요약(「5대 중 2대 선적 칸 부족」)으로 할지 ③ERP 처리됨 자동 완료를 켤지(지우지 않고 「오늘 끝난 것」으로만).
- ✅ jin 회신(11-11): ①입금률 % 도 같이 ②여러 대는 **요약 + 펼치기**(「5대 중 2대 선적 칸 부족」 → 누르면 대별 줄: 차량번호·차종·단계·RORO/컨테이너·포워딩사·VSL·빈 칸, 줄마다 [차량 열기]·[이 글 열기]) ③ERP 처리됨 = 「오늘 끝난 것」으로 내림(지우지 않음).
- 닫힌 건의 재발견 규칙(jin 질문 «완료된 건은 다음에 또 찾아내나?»): 자동 닫기는 **열린 요청만** 본다(resolves 없고 state 없는 것). 닫히면 `kakao_items.state=done`(사유 erp/reply)로 박혀 다음 읽기에 다시 안 본다. 사람이 [다시 할 일로] 되돌리면 그 건은 자동 닫기 대상에서 제외(`auto_close_opted_out`). 지금 「답 달림」 자동 후보는 박히지 않고 매 렌더 계산이라 표시 기간(7일) 동안 접힌 묶음에 계속 보인다 → ERP 처리됨과 같이 **박는 방식**으로 통일(생긴 날만 「오늘 끝난 것」, 다음 날부터 숨김, 「완료된 것 보기」 필터로 다시 볼 수 있게).
- ➕ **ERP 미등록 차량 → 「등록하세요」**(jin 11-11): 차량 서식(차량명/차량번호/차대번호 …)이 왔는데 차량번호·VIN 어느 것도 ERP 에 없으면 할 일 행에 「ERP 미등록 — 차량 등록 필요」 + 분야 **등록**. 판정은 **VIN 17자 우선**(말소 뒤 번호판이 바뀌거나 오타가 나도 VIN 은 남는다), VIN 이 없으면 차량번호. 「미등록 의심」으로 표시하고 다음 읽기 때 ERP 에 생겼으면 저절로 「등록됨」으로 닫힌다(ERP 처리됨 자동 완료와 같은 규칙). 서식이 아닌 한 줄 언급(「48조5021 저당 없습니다」)엔 안 띄운다 — 이미 등록된 차를 말하는 경우가 대부분.
- 🏷️ **분야 목록 확정안(jin 11-11)** = 등록 · 말소 · 통관 · 선적 · 입금 · **보험** · **서류** · 전체. 보험 = 보험 가입·해지·명세. 서류 = 면장·B/L·OBL·서렌더·인보이스·패킹리스트·통관서류 발송처럼 **문서를 만들고 주고받는 일**(통관이든 선적이든). 통관 = 면허·반입·신고 진행 자체, 선적 = 부킹·배차·VSL·ETA.
