# 바이어 현금 원장 (외화 입금 → 판매잔금 차감)

> **상태: 1~4단계 구현 완료 (2026-09-05) · 5단계(포털 미러)만 남음** — 기획 확정 = jin 2026-09-04 인터뷰 5라운드
> 진입점 = 이 문서. 「바이어 캐시」 · 「외화 입금 배분」 · 「현금 원장」 이라고 하면 여기부터 읽는다.

## 0. 무엇을 만드나 (jin 원문)

> 외화 입금된 거를 그 해당 바이어에게 주고 차감한다는 방식.
> 실무자가 바이어별로 **바이어(통화) − 캐시** 를 바이어 탭에서 기재 → 예) `2026-09-04 / 10,000 EUR`
> 그 10,000 EUR 를 바이어가 구매한 차량 N대에 각각 **판매잔금으로** 처리.
> 그러면 이 10,000 EUR 를 **어떻게 사용했는지 투명하게 보고 추적**할 수 있고,
> 남은 차량 대금이 얼마인지, 선적·수출신고번호·컨테이너로 묶인 차들의 남은 잔금이 얼마인지 볼 수 있다.

**최종 목적지는 은행권(펌뱅킹) 연동이다.** 이 기능은 그 **뒷단**이고, 앞단(은행)이 붙기 전에
**수동 기재**로 먼저 쓴다. 그래서 「입금 1건」의 모양은 나중에 은행 전문이 채워 넣어도
그대로 맞도록 잡는다. 참고 = 메모리 `project_firmbanking_cash_position`.

## 1. 확정 사항 (jin 답변 — 재논의 금지, 바꾸려면 여기부터 고칠 것)

| # | 물음 | 답 |
|---|---|---|
| 1 | 적립금을 재사용하나 | **아니다.** 「진짜 cash 가 들어온 걸 입력하고 그만큼만 쓴다」 — 별도 원장 |
| 2 | 어느 차에 얼마를 누가 정하나 | **실무자가 손으로** (자동 배분 없음) |

| 7 | 차단 범위 | **차량 판매탭 잔금 N행** + **채권관리 회수이력 「입금」** 2곳만 |
| 8 | 정정·취소 | **배분 행만 개별 회수** = 그 잔금 행을 지운다 |

| 10 | 미수 초과 배분 | **막는다.** 대신 남은 현금을 **적립금으로 전환**할 수 있게 |
| 11 | 묶음 축 | **컨테이너번호 · 수출신고번호 · B/L번호 · 선박명(VSL)** |

## 2. 데이터 — 원장을 「행」으로 잡는다

🚨 **적립금(`savings_statuses`)처럼 만들지 말 것.** 적립금은 배분 내역을 DB 에 안 갖고
**매 조회마다 원장 전체를 재생해 FIFO 를 계산**한다(`app/Services/SavingsLedger.php:41-135`).
그래서 「이 입금이 어느 차에 얼마」를 **조인·집계·엑셀·포털로 뽑을 수 없다.**
이 기능의 요구 1순위가 「투명하게 추적」이므로 **처음부터 행으로 저장**한다.

```
buyer_cash_receipts                       ← 입금 1건 (통장에 찍힌 그 건)
  id
  buyer_id        FK buyers, NOT NULL
  currency        enum(USD,JPY,EUR,GBP,CNY,KRW)
  received_date   date            -- 한국에서 받은 날
  amount          decimal(15,2)   -- 외화. ⚠️ 원화·환율 없음 (확정 #9)
  note            string nullable
  created_by      FK users nullable
  timestamps
  index [buyer_id, currency]

buyer_cash_allocations                    ← 배분 1줄 = 「이 입금에서 이 잔금으로 얼마」
  id
  receipt_id        FK buyer_cash_receipts, cascadeOnDelete
  final_payment_id  FK final_payments,      cascadeOnDelete   -- 잔금 지우면 배분도 사라짐
  vehicle_id        FK vehicles                                -- 조회 편의(비정규화, FP 로도 도달 가능)
  amount            decimal(15,2)   -- 외화
  created_by        FK users nullable
  timestamps
  index [receipt_id], index [vehicle_id]
```

- **입금 잔액** = `amount − Σ allocations.amount` — 조인 한 번. **캐시 컬럼 두지 않는다**(v1).
- **바이어 현금 잔액(통화별)** = 그 바이어·통화의 미소진 입금 합.
- 한 잔금이 **두 입금에 걸칠 수 있다**(FIFO) → 그래서 1:N 이 아니라 별도 테이블이다.

> 🧭 왜 `final_payments` 에 `receipt_id` 한 칸이 아니라 별도 테이블인가 —
> 잔금 하나가 여러 입금을 소진하는 경우가 실재한다(3,000 남은 입금 + 새 7,000 입금 → 10,000 잔금).
> 칸 하나면 그 순간 **어느 한쪽이 조용히 사라진다**.

## 3. 문지기 — 어디서 차감되나

**`FinalPayment` 모델 훅** 4개에 건다. 조건 판정은 **`BuyerCashService::gated()` 단일 출처**다 —
어디에도 옮겨 적지 말 것.

| 훅 | 하는 일 |
|---|---|
| `creating` | 확정 상태로 만들어지면 잔액 확인(부족하면 `DomainException`) |
| `created` | 확정분이면 FIFO 배분 행 생성 |
| `updating` | 확정으로 넘어가거나 확정분 금액이 바뀌면 잔액 확인 |
| `updated` | 확정분이면 재배분 / 확정이 풀리면 반환 |

삭제는 훅이 없다 — `buyer_cash_allocations.final_payment_id` 의 **DB cascade** 가 처리한다(§5).

왜 모델 훅인가: 서비스 계층에 두면 **새 생성 경로가 늘 때 조용히 빠진다**(SKILLS §8 #66 의 그 형태).
훅에 두고 **예외를 명시 플래그로** 여는 게 이 레포의 관례다(`$skipReceivableSync` · `$allowConfirmedMutation`).

⚠️ **모델 훅을 안 타는 구멍이 하나 있었다** — `ReceivableHistory::syncFinalPayment` 가 기존 잔금을
`FinalPayment::where(...)->update()`(query-builder)로 고친다. 확정분의 금액이 그렇게 바뀌면
배분이 그대로 남아 현금과 어긋난다 ⇒ 그 자리에서 `BuyerCashService::resyncAfterRawUpdate()` 를 부른다.

### 걸리는 것 (jin 이 지정한 2경로)

| 경로 | 왜 걸리나 |
|---|---|
| 차량 판매탭 「잔금 N+」 | `final_payments` type=`balance` 직접 생성 |
| 채권관리 회수이력 「입금」 | `ReceivableHistory::syncFinalPayment` 가 type=`balance` FP 를 미러 생성 |

### 안 걸리는 것 (제외 이유를 반드시 남긴다 — 다음 세션이 「구멍」으로 오해하고 막지 않게)

| 경로 | 제외 이유 |
|---|---|
| 판매탭 계약금·중도금·선수금1·수수료 | **type ≠ balance.** jin 명시 제외 — 계약금은 수출 전 선수금이라 성격이 다르다 |
| 재무 「이체·입금확정」 | **생성이 아니라 Draft 확정** (§4 참조) |
| 차량 간 자금 이체 | `transfer_id` 페어. 새 돈이 아니라 **차량 사이 이동** — 현금 풀과 무관 |
| 콘솔 적재(`ImportVehicles` 등) | 훅의 기존 관례대로 `auth()->check()` 가 false → 자동 통과 |

### 통화·차량 조건

- **입금 통화 = 차량 통화** 여야 소진된다. 다르면 그 입금은 이 차에 못 쓴다(확정 #3).
- 🚨 **KRW 차량은 게이트를 타지 않는다.** 국내 거래·원화 판매가 첫날부터 막히면 안 된다.
  ⇒ 게이트 조건에 `vehicle.currency !== 'KRW'` 를 넣는다.
- 바이어 판정 = **`vehicles.buyer_id`(판매 바이어) 하나뿐**. 통관(`export_buyer_id`)·선적(`bl_buyer_id`)이
  달라도 **무시한다** — 지금 미수 게이지·한도가 전부 `buyer_id` 를 쓰고 있고
  (`app/Models/Buyer.php:99-101`), 여기서 다른 축을 새로 만들면 숫자가 갈린다.

## 4. ✅ Draft 잔금 — 소진 시점 (2026-09-05 실측으로 확정)

**결론 = 재무 확정 시점(`confirmed_at` 이 채워지는 순간)에만 소진한다.**

기획 때는 열어뒀는데, 운영 코드에 실제로 넣어 보고 정해졌다:

```
채권관리 「입금」 저장 → 미러 판매잔금 생성
  → confirmed_at = NULL   (Draft)
  → 미수 9,200 → 9,200     (안 줄어든다)
```

즉 **채권관리 입금은 미수를 즉시 줄이지 않는다**(재무가 따로 확정해야 준다).
생성 시점에 현금을 빼면 그 구간이 **「현금은 줄었는데 미수는 그대로」**가 되어,
이 기능이 없애려던 혼란이 새로 생긴다. ⇒ **현금이 빠지는 시점 = 미수가 주는 시점**.

**실무상 어떻게 보이나**
- 재무·관리가 판매탭에서 잔금을 넣으면 **저장 즉시 확정**이라 그 자리에서 막힌다.
- 영업이 넣은 Draft·채권관리 입금은 **재무 확정 단계**에서 막힌다(적는 것 자체는 된다).

🔒 이 실측 사실 자체를 테스트로 박제했다 —
`BuyerCashGateTest::test_receivable_deposit_creates_a_draft_that_does_not_move_either_number`.
미러 잔금이 확정 상태로 바뀌면 그 테스트가 먼저 깨져서 이 전제를 다시 보게 된다.

💡 **막히기 전에 보이게** 했다 — 판매 탭 잔금 위에 「바이어 현금 잔액」을 띄운다.
   0 이면 붉은 박스 + 「바이어 탭 「현금」에서 입금을 먼저 기재하세요」.
   🚫 화면이 조건을 다시 판정하지 않는다(`BuyerCashService::gated` 단일 출처) —
   갈리면 「안내는 없는데 저장이 막히는」 형태가 된다.

## 5. 회수 — 잔금 행을 지운다 (확정 #8)

코드 실측(`app/Models/FinalPayment.php:126-137`):
- `transfer_id` 있는 행 = **항상 삭제 불가**(이체 void 흐름 별도).
- 확정된 행은 **2차 정산 마감(`closed`) 차량일 때만** 삭제 차단. **마감 전이면 자유 삭제**다.
- `FinalPayment::deleted` 가 `refreshCaches()` 를 부른다 → **미수는 자동 복원**된다(`:77`).

⇒ 회수 = 그 잔금 행 삭제. `buyer_cash_allocations.final_payment_id` 를 `cascadeOnDelete` 로 걸면
**배분 행도 같이 사라지고 현금 잔액이 자동 복원**된다. 별도 로직 불필요.
단, **삭제 사실은 `AuditLog::recordEvent`** 로 남긴다(돈이 되돌아가는 일이라 흔적이 있어야 한다).

### 5-B. 입금을 잘못 기재했을 때 (2026-09-05 추가)

jin: *«850 usd 를 잘못 기재했을 수도 있으니 지워지면 최근 10,000usd 이 나와야 할것같아»*

**이미 쓰인 입금도 지울 수 있다.** 지우면 그 몫을 **남은 다른 입금에서 FIFO 로 다시 채운다.**
- 덮을 현금이 없으면 **통째로 롤백** — 입금·배분 그대로 남고 사유를 보여준다.
  안 그러면 「판매잔금은 남았는데 현금은 안 빠진」 상태가 된다.
- **판매잔금 자체는 안 건드린다** — 돈이 들어온 사실은 그대로다.
- 🚫 종전처럼 「배분됐으면 삭제 금지」로 두지 말 것. 오기재를 고칠 방법이 없어진다.

## 6. 남은 현금 → 적립금 전환 (확정 #10)

미수보다 많이 배분하는 건 막는다. 대신 바이어 현금 탭에 **「남은 현금 N → 적립금으로」** 버튼 하나.
한 트랜잭션에서 ①`SavingsStatus` EARNED 생성 ②그 입금을 소진 처리.

> ✅ **전환 시 환율 = 받지 않는다(NULL).** (2026-09-05 jin 질문 → 확인하고 종결)
> 적립금의 `exchange_rate` 는 **원화 병기(표시)용일 뿐 정산에 안 쓰인다** — 적립금 사용분은
> `Vehicle::getSaleReceivedKrwAccumulatedAttribute`(`app/Models/Vehicle.php:2057-2059`)가
> **판매환율로 평가**한다(FX 중립). 게다가 현금 입금엔 애초에 원화를 안 받으므로 적을 값 자체가 없다.
> ⇒ NULL. 손으로 넣는 적립금도 환율이 선택 입력이라 같은 모양이고, 목록에 「환율 미입력」으로 뜬다.

- ⚠️ 행마다 조회하면 N+1 — 잔금 id 로 한 번에 묶어 읽는다.

### 7-2. 「바이어 정산현황」 화면 — `/erp/buyer-account` (2026-09-05 신설)

**위치 = 고객관리 › 바이어 ↓ 컨사이니** (jin 지정). 게이트는 **채권관리와 같다**(`canViewReceivables`)
+ 토글 ON. 꺼진 회사엔 메뉴도 화면도 없다(주소를 직접 쳐도 404).

🚫 **줄여서 「정산」이라고 부르지 말 것.** 이 ERP 의 「정산」은 **담당자 지급**이다.
   가이드·챗봇 카드에도 항상 「바이어 정산현황」 전체로 쓴다. 코드·영문은 `account`
   (en 에서 `settlement` 은 담당자 정산 모델 이름이라 그대로 쓰면 진짜로 헷갈린다).

구성 = ①통화별 남은 현금 ②통화별 받을 돈 ③묶음별 남은 금액 ④미수 차량 ⑤엑셀.
대상 = **그 바이어 · 미수 > 0 차량 전부**(거래완료 포함). 통화는 섞지 않고 나눠 보여준다.
컬럼 = 차량번호 · **차대번호** · 진행상태 · 총판매가 · 받은 돈 · **남은 금액** · 묶음 번호 4개.

- **바이어 선택 = 검색되는 콤보박스**(`x-erp.combobox`). 🚫 `select` 로 되돌리지 말 것 —
  바이어가 수백이라 스크롤로 못 찾는다. 가드 = `test_buyer_picker_is_a_searchable_combobox`.
- **검색은 `Vehicle::scopeSearchAny` 단일 출처**다(2026-09-05 차량관리 blade 에서 추출).
  🚫 조건을 옮겨 적지 말 것 — 두 벌이 되면 「차량관리에선 찾히는데 여기선 안 찾히는」 형태가 된다.

### 7-3. 묶음별 잔금
4축(컨테이너번호 · 수출신고번호 · B/L번호 · 선박명)으로 group by.
- **값이 정확히 같은 것끼리만** 묶는다. 정규화는 **앞뒤 공백 제거까지**.
- ⚠️ 컨테이너번호는 ISO 규격만 들어있지 않다 — `6.06_G RORO 11-27_10` 같은 **자체 관리코드가
  다수**(ssancarerp 실측 3,571건, SKILLS §8 #71-C). 표기가 흔들리면 묶음이 갈리는데
  **그건 버그가 아니라 데이터의 성질**이다. 합치려 들지 말 것.
- 빈 값은 「미지정」으로 따로 모은다.
- 🅿️ **인덱스는 실측 후에.** 조회가 바이어 스코프 안(수십 행)이라 4개 인덱스가 필요 없을 수 있다.
  느리면 그때 넣는다.

### 7-4. 엑셀
`throttle:data-export` · 끝에 `ExportLog::create` · 시트 2장(미수 차량 / 묶음별).
머리말에 바이어·기준시각·통화별 남은 현금 — 파일만 봐도 누구의 언제 현황인지 알 수 있게.
🚨 **화면 필터 ↔ export 가 갈리면 안 된다** — 조건을 옮겨 적지 말고 **같은 서비스**를 쓴다
   (`BuyerAccountService`). 화면 검색(`q`·`vin`)도 그대로 넘긴다. 가드 = 행 수 대조.
🚨 문자 칸은 전부 `TYPE_STRING` — 컨테이너·B/L 이 수로 변해 앞자리 0 이 날아가는 것과
   `=` 로 시작하는 값이 수식으로 실행되는 것을 막는다.

## 8. 포털 미러 (ssancar.com) — 확정 #14

`PortalVehicleController::COLUMNS` 화이트리스트에 추가:
- 차량별 **남은 금액** — 이미 나가는 `unpaid_amount` 로 충족(추가 없음)
- **입금 내역 + 배분** — 수령일 · 통화 · 금액 · 「어느 차에 얼마」

- 바이어 **자기 돈**이라 PII·영업비밀이 아니다. 금지 목록(매입가·마진·정산·RRN·한도)과 무관.
- **미수 닫힘 항등식은 안 바뀐다** — 배분은 결국 확정 잔금이라 `paid` 안에 이미 들어 있다.
  🚫 새 항을 항등식에 더하지 말 것(SKILLS §8 #64).
- ⚠️ **크로스 레포**: 실제 발행 스펙 합의는 **ssancar 세션**에서 정본 문서에 올린다
  (`docs/integration/ssancar-portal-collab.md` 절차). 이 문서는 ERP 쪽 의도만 적는다.

## 9. 토글

- 키 = `buyer_cash_enabled_{template_set}` (회사별). **기본 OFF** — 신규 기능이라 켠 회사만 적용.
- 변경 권한 = **super 전용**. 변경 시 `AuditLog`(돈에 영향 있는 토글이므로).
- OFF 면 **게이트가 아예 안 돌고** 현금 탭·표·엑셀·포털 항목이 안 보인다.
  → 값 자체를 0/null 로 만드는 기존 패턴(`Buyer::effectiveUnsecuredLimit()`)을 따른다.
- **전환 마이그레이션 없음**(확정 #13) — 회사가 「미배분 현금 0」인 날 켠다.
  🚨 켜기 전에 **그 회사에 미배분 현금이 정말 없는지** 화면에서 확인할 수 있어야 한다.

## 10. 착수 순서 (제안)

1. ✅ **완료** — 마이그레이션 2개 + 모델 2개 + 토글(기본 OFF). 동작 변화 없음.
2. ✅ **완료** — 바이어 「현금」 탭(입금 기재·조회·배분 내역). 토글 OFF 면 탭이 안 뜬다.
3. ✅ **완료** — 게이트 + FIFO 배분 + 회수(cascade) + 판매 탭 현금 잔액 표시.
4. ✅ **완료** — 「바이어 정산현황」 화면(고객관리 › 바이어 아래) · 묶음별 4축 · 엑셀 · 공용 검색.
5. ⬜ 포털 미러 (ssancar 세션과 합의 후)

> ⚠️ 순서를 §10 초안에서 **2↔3 바꿨다** — 문지기를 먼저 넣으면 토글을 켜는 순간
> 현금을 넣을 방법이 없어 전부 막힌다. 입금 화면이 먼저다.

## 11. 반드시 만들 가드

- 현금 부족 시 잔금 생성이 **막히는지** / 토글 OFF 면 **안 막히는지**
- 채권관리 입금 1건 → 미수 **한 번만** 감소, 현금 **한 번만** 감소
  (FP 생성이 `ReceivableHistory(method=deposit)` 를 자동 미러하는데(`FinalPayment.php:154-166`),
  그 method 는 `Vehicle::MIRRORED_RECEIVABLE_METHODS` 라 미수 계산에서 빠진다 —
  **이중계상 없음을 테스트로 박제**한다)
- KRW 차량·통화 불일치는 **게이트를 안 탄다**
- 잔금 삭제 → 배분 행 사라지고 현금 잔액 복원 → 미수 복원 (end-to-end)
- 한 잔금이 **두 입금에 걸치는** FIFO
- 마감(`closed`) 차량은 배분 대상에서 제외되고 그 사유가 화면에 보인다
- 화면 필터 ↔ 엑셀 결과 일치
- 정적: `type='balance'` FP 를 만드는 **새 경로가 생기면** 게이트를 타는지
