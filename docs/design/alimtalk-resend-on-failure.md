# 알림톡 실패 재전송 버튼 — 조사 (jin 2026-09-04, **착수 전**)

> jin: *"월배치 정산지급 승인 알림톡처럼 실패할 경우 재전송할 방법이 필요하다. 실패면 월배치 화면
> 해당 드로어에 재전송 버튼이 활성화되면 좋겠다. 별건으로 확인해줘 — 앞으로 한 번이라도 더 실패하면 만들자."*
>
> **아직 만들지 않았다.** 이 문서는 「만들 때 바로 시작하려고」 막히는 지점까지 확인해 둔 것이다.

## 0. 결론 한 줄

**지금 구조로는 못 만든다.** 알림톡 로그와 월배치를 잇는 고리가 없어서, 월배치 화면이
「이 배치의 발송이 실패했나」를 물어볼 방법이 없다. 그 고리부터 만들어야 한다.

---

## 1. 🚧 막히는 지점 — 로그가 어느 배치 것인지 모른다

`alimtalk_logs` 가 가진 관계는 **`vehicle_id` · `user_id` 둘뿐**이다(`AlimtalkLog::$fillable`).

그런데 월배치 알림톡은 이렇게 보낸다 (`SettlementPayoutBatch::notifyPayoutRequest()`):

```php
$svc->send('erp_payout_request', $user->phone, $vars, ['user_id' => $user->id], [ ...버튼 ]);
```

⇒ 남는 건 **수신자 user_id 뿐**이고 배치 id 는 어디에도 없다.
「배치 #3 의 발송이 실패했나」를 물으면 답할 수 있는 컬럼이 없다.

⚠️ 시간·수신자로 추정하는 건 **안 된다** — 같은 승인자에게 여러 배치가 갈 수 있고,
재발송·계단 전진으로 같은 조합이 여러 번 생긴다. 실패 1건을 엉뚱한 배치에 붙이면
「멀쩡한 배치에 재전송 버튼이 뜨는」 형태가 된다.

### 고리를 만드는 세 가지 방법

| 안 | 내용 | 평 |
|---|---|---|
| **A. morph 2컬럼** `related_type` + `related_id` | 어떤 모델에도 붙는 범용 고리 | ⭐ **추천** — jin 의 「앞으로 한 번이라도 더」에 맞는다. 다른 알림톡도 같은 방식으로 재전송을 붙일 수 있다 |
| B. `settlement_payout_batch_id` 전용 컬럼 | 월배치만 | 좁다. 다음에 또 같은 요구가 오면 컬럼이 또 는다 |
| C. 스키마 무변경 · 시간+수신자 추정 | 마이그레이션 없음 | 🚫 위 이유로 부정확 |

**A 를 고르면**: `vehicle_id` 는 그대로 둔다(이미 화면이 쓴다). morph 는 **추가**만 하고,
새로 보내는 곳부터 채운다. 마이그레이션은 컬럼 2개 추가라 3사 배포 위험이 낮다.

---

## 2. 화면 — 언제 뜨고 무엇을 하나

**위치**: 월배치 화면 배치 카드(드로어).

**노출 조건** — 그냥 항상 두면 안 된다. 「그 배치 × **현재 계단**」의 마지막 발송이 실패했을 때만.
성공했는데 버튼이 보이면 사람이 눌러서 중복 발송한다.

```
배치 #3 · 2026-08 · 대표 승인 대기
  ⚠️ 승인 요청 알림톡이 실패했습니다 — 등록된 버튼과 다름 (09-02 11:40)
     받는 사람: 최고관리자 ...9977                     [ 다시 보내기 ]
```

🔑 **마지막 실패 사유를 같이 보여준다.** 사유가 K108 처럼 「고쳐야 나가는」 것이면
재전송해도 계속 실패한다 — 사유 없이 버튼만 있으면 사람이 헛되이 반복한다.

**동작**: `notifyPayoutRequest()` 재호출(이미 멱등하게 동작한다 — 2026-09-04 수동 재발송으로 실증).
새 5일 서명 링크가 나가고, 옛 링크도 만료까지 살아 있다(같은 배치·같은 승인자라 무해).

**권한**: 제출할 수 있는 사람(`canSubmitPayoutBatch`) + super. 승인자 본인은 불필요.

**가드**:
- 승인 완료·반려된 배치는 버튼 없음
- 연타 방지 — 최근 N분 내 재발송이 있으면 비활성(사유 표시)
- 재발송도 `AlimtalkLog` 에 남아야 한다(누가 언제 다시 보냈나)

## 3. 이미 있는 것 — 중복이 아니라 갭 메우기

실패는 **이미 사이드바 배지로 뜬다**(`AlimtalkLog::scopeNeedsAttention()` = 실패/미도달 중 미확인).

🚨 **그런데 그 배지는 super 에게만 보인다**(`sidebar.blade.php:119` — 알림톡 로그 메뉴가
super 전용이라 배지 계산도 같이 좁혔다). 즉 **관리·업무관리자는 발송 실패를 볼 방법이 아예 없다.**

⇒ 월배치 화면 버튼의 진짜 값어치는 「재전송」보다 **「그 일을 하는 사람이 그 자리에서 실패를 본다」** 는 것이다.
2026-09-02 실패가 이틀 방치된 것도 제출자(이새롬, manager)에게는 보이지 않았기 때문이다.

🚫 **다만 배지를 관리·업무관리자에게 열지 말 것 — jin 2026-09-04 「이건 나만 볼려고」.**
   super 전용은 실수가 아니라 **의도**다. 재제안 금지.
   ⇒ 그러므로 이 기능을 만들 때도 **사이드바 배지는 그대로 두고**, 월배치 화면 안에서만
     그 배치의 실패를 보여준다(제출자가 자기 배치 상태를 보는 것과, 전사 실패 목록을 보는 것은 다르다).

## 5. 착수 시 순서 (제안)

1. `alimtalk_logs` 에 `related_type` · `related_id` 추가(마이그레이션) + `BizmAlimtalkService::send()` 의
   `$context` 로 받아 저장
2. `notifyPayoutRequest()` 가 배치를 context 로 넘김
3. 월배치 화면 — 배치별 마지막 발송 상태 조회 → 실패면 경고줄 + [다시 보내기]
4. 가드: 상태·권한·연타·재발송 로그
5. (선택) 같은 고리를 다른 알림톡에도 — 그때는 화면마다 붙이면 된다

**미결**: 연타 방지 간격 · 실패 확인(acknowledge)을 이 버튼에서도 할지 · 관리에게 사이드바 배지를 열어줄지.
