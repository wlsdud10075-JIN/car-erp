# board 발 매입 락 해제 요청 → ERP 승인큐 + 알림 벨 「승인 대기」 구역

> 상태: **ERP 구현 완료(dev, 2026-11-19 — jin «지금 board 매입 락 승인건 진행하자»), master 배포 대기.** 규격 정본 = `docs/integration/board-portal-api.md` §17. board 구현은 board dev 에 있음(ERP 배포 통지 뒤 배포).

> 관련: `docs/integration/board-collab.md` §3 2026-11-19 · board 쪽 구현은 board 세션 몫.

## 1. 왜

board 사용 전에는 바이어 미수가 높아도 ERP 차량 저장 때 「관리자 사유」를 적고 등록했다(1대 미수 100% 인 바이어의 2·3번째 차).
지금은 board 가 매입 입구라 락 걸린 바이어는 board 에서 구매확정이 그냥 막히고 우회 길이 없다.
⇒ 그 「사유 쓰고 등록」을 **승인 절차**로 바꾼다. 판단하는 것은 하나 — **이 바이어로 몇 대를 더 등록하게 할 것인가**(jin «단순히 차량을 등록할 수 있느냐 없느냐»). 금액은 판단 대상이 아니다.

## 3. 확정 (jin 2026-11-19)

|---|---|---|

| 3 | 범위 | 🔀 **바이어 + 등록 대수 N**(jin 11-19 오후 «1대 등록하고 무조건 1대만 더 등록하는 게 아니니까» — 구: 차 1대·1회). 요청에 「N대 더 등록」이 담겨 오고, 승인자는 **줄여서 승인**할 수 있다(5대 요청 → 3대). 상한 없음. 그 바이어로 board 구매확정할 때마다 1대 차감(락이 걸렸는지 따지지 않는 **단순 카운트**), 0 이 되면 다시 막힌다. 더 하려면 재요청 |
| 4 | 유효기간 | 승인 후 **7일**(jin «등록 절차니까») — 남은 대수는 소멸 |
| 5 | 끝나는 경우 | 대수 소진 · 7일 경과. 승인은 바이어에 걸려 있어 다른 바이어에는 안 쓰인다. **금액 수정은 무관** — 승인 전·후·ERP 등록 뒤 모두 자유 |
| 6 | 요청 버튼(board) | 등록 영업 본인 + 관리 대리. 실제 누른 사람 이름을 같이 남긴다 |
| 7 | 거절 뒤 재요청 | 가능, 횟수 제한 없음(매번 사유 필수, 이력 남음) |
| 8 | 승인 화면 | 바이어 · **요청 대수(승인자가 고칠 수 있는 칸)** · 요청자(+누른 사람) · 사유 · 요청이 시작된 차(차량번호·차명, 참고) + **ERP 가 승인 시점에 계산한** 바이어 미수·미수율/락 기준·진행 대수. 승인 뒤에는 「N대 중 몇 대 사용」. 차값·판매가·통화·환율·첨부는 받지 않는다 |

## 4. 알림 벨 「승인 대기」 구역

- 벨 안을 두 구역으로: 위 = 승인 대기(빨강), 아래 = 종전 알림 그대로.
- 위 구역은 **[확인]으로 안 사라진다** — 승인·거절돼야 사라진다. 누르면 승인큐의 그 건으로.
- 접힌 벨에 「승인 N」을 일반 알림 숫자와 따로 표시. 새 건이 오면 보고 있는 사람에게 토스트 1회.
- 보는 사람: 승인권자(관리 이상)만. 본인이 올린 건은 회색 「내가 올린 요청」(승인 불가). 승인권 없는 수출통관·재무는 자기가 ERP 에서 올린 요청의 진행만.
- 올리는 범위 = **승인큐 전체**(이번 매입 락 + 정산 지급·미입금 우회·자금 이체 등 `scopeActionable`). 벨과 승인큐 화면·사이드바 뱃지가 같은 집합을 봐야 한다.
- 🚫 월정산 결재 대기는 이번에 안 올린다. 나중에 붙일 땐 **업무관리자 이상에게만**(jin).
- 벨 목록 세로 높이 60vh → **80vh**(jin «1/3 더»). 폭은 그대로.

## 5. 구현 메모 (착수 때)

- `ApprovalRequest` 새 종류(가칭 `board_purchase_lock`), target = Buyer, payload = { requested_count, approved_count, used_listing_ids[], 시작 차(purchase_listing_id·vehicle_number·차명, 참고용), salesman_email, requested_by_name, 사유 }. 같은 바이어에 살아 있는 승인(대수 남음·7일 이내)은 한 건만 — 남아 있는데 또 요청하면 어떻게 할지(거절/합산)는 착수 때 jin 에게 확인. 승인 화면의 미수 숫자는 payload 가 아니라 `PurchaseRegistrationGate`/`Buyer::receivableGauge()` 로 그때 계산.
- 내부 API(읽기 HMAC 틀): 요청 생성 `POST` · 상태 조회 `GET ?buyer_id=`(남은 대수·만료 시각 — board 가 구매확정 직전 재확인 + 결과 폴링). ERP → board 웹훅 경로는 없다(board 확인).
- 차감: purchase-sync 가 그 바이어로 들어오면 `purchase_listing_id` 를 `used_listing_ids` 에 넣고 1대 차감(같은 listing 재전송은 한 번만 — 멱등). 다 쓰면 `used_at`. ⚠️ board 구매확정 → purchase-sync 사이에 두 대가 동시에 나가면 초과할 수 있다 — 차감 시점(구매확정 때 예약 호출 vs sync 도착)은 착수 때 규격에서 확정. 수신부가 락을 새로 검사하지는 않는다(돈이 나간 뒤라 거부해 봐야 늦다) — 승인 id 를 감사에 연결.
- 벨: `TaskAlarm` 에 넣지 않고(차량 FK 전제) 벨 컴포넌트가 pending `ApprovalRequest` 를 직접 읽는 쪽이 단순하다 — 착수 때 확정.
- board 가 바꿀 것: /auction 드로어 🔒 바이어에서 [ERP 승인 요청](대수 + 사유) → 상태 칩(요청중/승인 N대 중 k대 남음/거절+사유) → 남은 대수가 있는 바이어는 구매확정 통과. 요청 때 금액을 미리 저장하던 초안은 불필요해졌다.

## 6. 착수 뒤 추가 결정 (jin 2026-11-19 저녁)

- 대수가 남아 있어도 **추가 요청 가능, 승인되면 더한다**(승인 건마다 자기 7일, 먼저 만료되는 것부터 차감). 대기 건이 있으면 새 요청은 안 받는다.
- 관리가 board 에서 **대리로 누른 요청은 그 사람이 승인할 수 없다**(`requested_by_email`).
- 차감 시점 = **차가 ERP 에 등록될 때**(purchase-sync 새 차량). 동시 확정으로 1대 초과할 수 있음을 알고 정함 — 초과해도 등록은 받고 감사에 남긴다.
- board 에서 구매확정을 되돌려도 **대수는 안 돌려준다** · 차를 지우고 재등록해 다시 구매확정하면 **한 번 더 차감**.
- 요청자가 ERP 계정 없는 영업일 수 있다(karabaerp 활성 영업 15명 중 12명) → `approval_requests.requester_id` nullable(마이그 1).
- 대기 중인 요청은 **board 에서 거둘 수 있다**(jin «3대를 30대로 잘못하면 그쪽에서도 취소») — 결정된 건은 못 거둔다. 거둔 뒤 바로 재요청.
- 벨: 바이어 이름이 길면 제목이 잘려 대수는 둘째 줄에 · 승인큐 화면에서는 승인 건 때문에 벨을 자동으로 펼치지 않는다(버튼을 가린다).
