> 🔎 **지금 어느 방식인지는 문서로 판단하지 않는다 — 실측한다.** 2026-11-20 실측: 운영 3사 설정 비어 있음(= 환차 포함), `fx_excluded = true` 인 정산 0건. 로컬은 확인용으로 켜 둠(정리 금지).

### 1. 정산환율 — 단일 출처 `Settlement::settlementRate()`
🚫 정산 계산에서 `Vehicle::settlement_exchange_rate` 를 직접 부르지 않는다. 판매금원화·건당 판정·월정산 환산·2차 분해가 전부 `settlementRate()` 를 거친다.

| | 환차 포함 (지금 운영 3사) | 환차 제외 (2026-12 귀속월부터 예정) |
|---|---|---|
| 정산환율 | 실효 입금환율 `Vehicle::settlement_exchange_rate` | 판매환율 `vehicles.exchange_rate` |
| 프리랜서(비율) 정산 | 환차가 마진 공식(× 0.9 × 비율)을 통과해 담당자와 나뉜다 | 환차가 안 들어간다 |
| 회사 몫 환차 | 따로 없음(총마진에 이미 들어 있다) → `companyFxKrw()` = 0 | 실현 환차 **전부**(운임비분 포함) → `companyFxKrw()` 가 회사이익에 더해진다 |
| 사내직원(건당) | 건당액은 「건당 판정 마진」으로 정해진다 — 환율이 등급 경계를 넘기거나 고액 매입의 비율 구간이면 금액이 움직이고, 그 밖엔 영향 없다 | 환율로는 안 움직인다 |

- **실효 입금환율** = (실입금 원화 + 미수 외화 × 판매환율) ÷ 총판매가(외화).
  완납이면 실입금 원화 ÷ 총판매가. 미완납은 받은 몫만 실제 환율, 남은 몫은 판매환율로 섞는다. 과입금(미수 음수)은 완납으로 본다.
  원화 차·판매환율 0·총판매가 0 이면 판매환율 그대로.
  실입금 원화 안에서 **판매환율로 평가되는 몫**: 환율이 빈 확정 입금 줄 · 채권관리 회수(현금·상계·기타) · 적립금 사용 · 차량 간 자금 이체로 생긴 입금 줄.
- **환차 포함일 때 운임비의 환차는 회사 몫**이다 — 실효환율은 총판매가(운임비 포함) 기준인데 정산 기준액에는 운임비가 없다.
- **실현 환차** `Settlement::computeExchangeDifference()` = 실입금 원화 − 받은 외화 × 판매환율. 원화 차는 0, 판매환율이 없으면 계산 불가(null).
- **회사 몫 환차** `Settlement::companyFxKrw()` = 환차 제외 정산이면 위 실현 환차(반올림, 계산 불가는 0), 아니면 0.
- **회사이익** `Settlement::company_net` = 총마진 − 실지급액 − 발송비 + `companyFxKrw()`. 회사 몫 환차는 사람별 기여에는 안 들어가고 합계에서만 더한다.
- **내수 정산**은 환율과 무관하다(판매금원화 = 총판매가, 항상 환차 포함 쪽).
- **karaba** 프리랜서 정산액은 `settlementRate()` 를 안 거친다 — 항상 판매가 × 판매환율(tier 공식)이라 방식과 무관하다. 다만 `total_margin`·`companyFxKrw()`·`company_net` 은 karaba 에서도 방식에 따라 갈린다.

### 2. 어느 방식인가 — 정산마다 박제된다 (`settlements.fx_excluded`)
```
판정 = 귀속월(attributed_month) ≥ 시작 귀속월(Setting::settlementFxExcludedFrom(), 'Y-m', 회사별)
```
- 🚫 **`fx_excluded` 컬럼을 직접 조회하지 않는다 — `Settlement::fxExcluded()` 를 쓴다.** 박제값이 있으면 박제값, 없으면 설정으로 판정하고, 내수는 박제값과 무관하게 항상 환차 포함이다(배치 밖에서 지급된 내수 정산은 컬럼에 true 가 들어갈 수 있다).
- 설정이 비어 있으면 **박제 안 된** 정산은 전부 환차 포함. 귀속월이 빈 정산도 박제값이 없으면 환차 포함.
- **박제 시점** = 월정산 제출(`pinFxForIds` — 아직 안 정한 정산만) 또는 지급(paid 전환). 11-17 마이그레이션이 그때까지의 배치·지급·마감 정산을 false 로 박았다.
- 반려되면 아직 지급 안 된 정산의 박제가 풀린다(`fx_excluded = null`).
- ⇒ 설정을 나중에 바꿔도 **이미 제출·지급된 정산은 안 움직인다.** 미래 값을 미리 넣어도 귀속월로 판정하므로 그때부터 적용된다.
- 설정 위치 = 기능설정 「💱 환차 · 판매잔금 환율」(시스템관리자만).

### 3. `exchange_difference_krw` 는 지급액이 아니다
2차 마감 순간의 실현 환차(`computeExchangeDifference()`)를 고정해 둔 감사·참고 기록이다. **어느 방식에서도 지급액에 더하지 않는다.**
`companyFxKrw()` 와 식은 같고, 저장값은 마감 뒤 들어온 돈이 반영되지 않는다는 점만 다르다(마감 시점 환율로 다시 평가하지 않는다 — `exchange_rate_at_close` 는 쓰이지 않는 칸이다).

2차 정산이 다음 달로 넘기는 것 = **마감 실지급액 − 지급 때 박제한 실지급액** 전부다. 대부분 비용 변동분이고, 지급 뒤 판매가·판매환율 수정, 서류비·발송비·기타공제 변동, 사내직원 등급 재평가도 같이 넘어간다. 환차 포함 정산은 지급 뒤 입금으로 생긴 환차분도 넘어간다. 환차 제외 정산은 입금 환율로는 환차분이 안 생긴다. 지급 스냅샷이 없는 행은 이월 0.

| 무엇 | 켤 값 | 켜면 |
|---|---|---|
| ① 정산 환차 제외 | 시작 귀속월 `2026-12` | 12월 처리분(2027-01-10 정산)부터 담당자 정산에 환차가 없고 회사가 전부 가진다 |
| ② 판매잔금 환율 자동 기록 | 시작일 `2026-12-01` | 판매탭·채권관리의 입금 환율 **입력칸**이 사라지고(판매탭은 값만 읽기 전용으로 보인다), 저장 때 서버가 환율을 적는다 |
| ③ 환율 종류 | `receive`(송금 받으실 때, 기본) / `base`(매매기준율) | 은행 우대율 확인 뒤 jin 이 고른다 |

- ② 가 적는 값 = **입금일보다 앞선 가장 최근 마감 환율**(`DailyExchangeRate::closingBefore` — 전날 값이 아직 없으면 그 전 영업일). `FinalPayment::autoRateFields()` 가 `exchange_rate` + 출처 `rate_source_date`·`rate_kind` 를 돌려준다.
- ② 가 적용되는 줄 = 새 줄 · 미확정 줄의 입금일이 바뀐 때 · 미확정인데 환율이 빈 줄. **확정된 줄과 시작 전에 사람이 적은 줄은 안 건드린다.**
- ② 를 **안 타는 입금 줄** = 판매탭 4항목(계약금·중도금·선수금·수수료 — 판매환율, 즉시 확정) · 차량 간 자금 이체(환율 없음 → 판매환율 평가) · 원화 입금.
- 입금일 전 환율 행이 하나도 없으면 환율을 **비우고**(null — 계산은 판매환율로 떨어진다) 경고 로그를 남긴다. 미확정 줄의 날짜를 바꾼 경우 기존 환율도 지워진다.
- ② 의 판정 `Setting::paymentRateAutoActive()` 는 **오늘 ≥ 시작일**이다(입금일 기준이 아니다 — 시작 뒤에 입력한 과거 날짜 입금도 자동 기록). 화면 칸 숨김과 저장 경로가 같이 본다 — 갈리면 칸은 숨겼는데 사람 값이 저장된다.
