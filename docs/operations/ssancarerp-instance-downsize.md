# ssancarerp AWS 인스턴스 다운사이징 검토 (2026-09-18 실측)

> jin: *「ssancarerp AWS 가 월 44달러로 너무 비싸서 heymanerp처럼 월 11달러 짜리로 변경해야 하는데…
> ram이 4gb → 1gb로 변경돼. 그로인한 문제는 없을지?」*
> 🎯 **결론 = 다운사이징은 하되 1GB·2GB 가 아니라 4GB.** 근거는 아래 실측.
> 🚫 **아직 아무것도 안 바꿨다.** 읽기 전용 조사만 했다.

## 1. 🚨 먼저 정정 — 사실관계 3개가 달랐다

| jin 이 알고 있던 것 | **실측** |
|---|---|
| 현재 RAM **4GB** | **8GB** (`free -m` total 7,818MB · 2 vCPU · 디스크 154GB) |
| heymanerp 는 **1GB** | **4GB** (3,834MB · 2 vCPU · 77GB) |
| 서버를 새로 하면 **IP 가 바뀐다** | **Lightsail 고정 IP 는 떼서 새 인스턴스에 붙일 수 있다 → 안 바뀐다** |

⇒ *「heymanerp 처럼」* = **4GB** 다. 1GB 가 아니다. $11 이 맞다면 그건 **4GB 요금**이므로
   ssancarerp 도 4GB 로 내리면 같은 값이 된다. (요금제 확인은 콘솔에서 — SSH 로는 못 본다.)

## 2. 🏋️ 두 서버 차이 — **board 는 양쪽 다 있다** (2026-09-18 정정)

> ⚠️ **처음에 「heymanerp 엔 board 가 없다」고 적었는데 틀렸다.** jin 지적 후 `nginx -T` 로 직접 확인.
> `systemctl` 의 supervisor 워커 수만 보고 추정한 것이 원인이다 — **사이트 구성은 nginx 로 봐야 한다.**

| | ssancarerp (8GB · $44) | heymanerp (4GB) |
|---|---|---|
| ERP | `heymancar.com` · DB **48.2MB** | `heysellcar.com` · DB **20.9MB** |
| **board** | `board.heymancar.com` · DB 0.7MB | **`board.heysellcar.com` · DB 2.4MB** ✅ 있다 |
| **3사 공용 NICE 게이트웨이** | **`/provide/api/nice-lookup/`** | ❌ 없다 |
| 구 Django(gunicorn) | `ssancar-erp.service` (트래픽 0, 제거 대기) | ❌ 없다 |
| 큐 워커 | 2개 (board + car-erp) | 1개 (board) |
| php-fpm max_children | 14 | 10 |
| 실사용 메모리 | **1,600MB** | **1,417MB** |

🔑 **실제 차이는 둘뿐이다 — NICE 게이트웨이와 구 Django.**
   그 외 스택(ERP + board + MySQL + nginx + php-fpm)은 **같다**.
   ⇒ **heymanerp 가 같은 스택을 4GB 에서 1,417MB 로 돌리고 있다는 것이 4GB 판정의 직접 근거다.**

⚠️ **`/provide/api/nice-lookup/` 은 3사 ERP 가 전부 이 서버로 부른다**(CLAUDE.md §15).
   heymanerp·karabaerp 의 차량조회가 여기를 거친다 — 이 서버가 죽으면 **3사 조회가 같이 죽는다.**

## 3. 💾 메모리 — **1GB 불가 · 2GB 위험 · 4GB 안전**

> ⚠️ **아래 「피크 2.6GB」는 과대평가다 — §3-B(2026-09-21) 에서 정정했다.**
>    워커 메모리를 RSS 로 세어 공유 opcache 를 14번 중복 계산했다. 실제 피크는 **약 1.3GB**다.
>    결론(4GB)은 그대로지만 **여유는 훨씬 크다**. 판단에 쓸 숫자는 §3-B 를 볼 것.

```
현재 (한가할 때)   총 7,818MB · 사용 1,600MB · 여유 6,217MB · 스왑 사용 0 · OOM 이력 0
구성               mysqld 578MB + php-fpm 7개 ≈ 640MB + gunicorn + 워커 2 + nginx/OS
피크 추정          mysqld 578 + php-fpm 14개×110=1,540 + Django ~150 + 워커 160 + OS 200 ≈ 2.6GB
```

| 번들 | 판정 |
|---|---|
| **1GB** | 🚫 **불가.** MySQL 혼자 578MB. php-fpm 3~4개만 떠도 OOM. |
| **2GB** | ⚠️ **위험.** 피크 2.6GB 추정. `max_children` 을 14→6 으로 줄여야 하는데 **§4 때문에 치명적**. |
| **4GB** | ✅ **안전.** heymanerp 가 4GB 에서 1,417MB 로 돈다. 여유 2배 이상. |

## 3-B. 🔬 **사용자 수를 알고 다시 쟀다 (2026-09-21)** — 결론 안 바뀜, 근거가 더 단단해짐

> jin: *「board를 대략 10~20명 쓰고, erp를 대략 6명이 쓸거고, heyman은 board를 최소 5명, erp를 2명이 쓰거든?
> 근데 ssancarerp가 ram이 높잖아? 이걸 heyman처럼 4gb로 내렸을 때 문제는 없어?」*

**§3 의 「피크 2.6GB」 추정이 과대평가였다.** 워커 메모리를 RSS 로 셌기 때문이다.

```
php-fpm 워커 6개   RSS 합 572MB (97MB/워커)  ←  §3 이 쓴 숫자
                   PSS 합 131MB (21MB/워커)  ←  실제 물리 메모리
```

🔑 **차이의 정체 = 공유 opcache 128MB 가 워커마다 중복 계산된 것.** 워커를 하나 더 띄울 때
실제로 더 드는 메모리는 **약 21MB**이지 100MB 가 아니다. ⇒ `max_children` 14 를 꽉 채워도
php-fpm 전체가 **300MB 안쪽**이다(1,540MB 가 아니다).

**실측 대조 (2026-09-21 09시대 = 평일 피크)**

| | ssancarerp (8GB) | heymanerp (4GB) |
|---|---|---|
| 예정 사용자 | board 10~20 · **erp 6** | board 5 · **erp 2** |
| `pm.max_children` | **14** | 10 |
| 워커 PSS | 6개 131MB (21MB/워커) | 5개 134MB (27MB/워커) |
| mysqld RSS / buffer_pool | 594MB / **128MB** | 564MB / 128MB |
| 실사용 메모리 | **1,576MB** | 1,417MB |
| swap | 2GB (사용 0) | 2GB (사용 0) |
| load average | 0.18 | 0.04 |
| **분당 최대 워커초** | **30.3 → 동시 0.5개** | 22.1 → 동시 0.37개 |

🚨 **핵심 — 사용자 수는 메모리 천장을 안 올린다.**
피크 메모리는 `max_children` 가 정한다(14개). 사람이 26명이든 6명이든 **워커는 14개를 안 넘는다.**
사용자가 늘어서 생기는 것은 **줄서기(지연)**이지 OOM 이 아니다.

**그럼 14개로 26명이 되나 — 리틀의 법칙으로 환산**
```
평균 응답 0.57초 · 워커 14개
사용자가 5초에 한 번 클릭   →  1인당 0.114 워커  →  14 ÷ 0.114 ≈ 123명까지
사용자가 2초에 한 번 클릭   →  1인당 0.285 워커  →  14 ÷ 0.285 ≈  49명까지
```
현재 실측은 **피크에도 동시 0.5개**다. 26명은 한참 안쪽이다.

**4GB 에서의 피크 재계산 (Django 제거 후)**
```
mysqld 594 + php-fpm 14개 ≈300 + 큐워커 2개 129 + nginx·supervisor·OS ≈250  ≈  1.3GB
4GB 실제 가용 3,834MB  →  여유 2.5GB + 스왑 2GB
```

⇒ ✅ **4GB 로 내려도 문제 없다.** heymanerp 가 같은 스택을 4GB·1,417MB 로 돌리고 있고,
   ssancarerp 는 사용자가 3~4배여도 **워커 점유가 0.5/14** 라 같은 상자에 여유가 크다.

**🚫 하지만 이것만은 하지 말 것 — `max_children` 을 줄이는 것.**
4GB 로 내리면서 「메모리 아끼자」고 14 → 6 으로 줄이면 **NICE 조회가 동시 4개까지 워커를 8~14초 묶으므로
남는 워커가 2개**가 된다(§4·§15). 14 는 4GB 에 충분히 들어가므로 **그대로 유지**한다.

**함께 챙길 것**
- **스왑 2GB 를 새 인스턴스에도 만들 것** — 지금 양쪽 다 있고 사용 0 이다. 안전망을 빠뜨리지 말 것.
- opcache 128MB · innodb_buffer_pool 128MB **그대로**(DB 48MB 라 충분).
- 구 Django(gunicorn 4프로세스 ≈196MB) 제거 — 트래픽 0.
- CPU 는 안 바뀐다(양쪽 다 2 vCPU · load 0.18 / 0.04).

## 4. 🐢 지금 느린 이유 — **RAM 이 아니다. 워커 점유다**

jin: *「지금도 화면에 100개로 놓고 보면 ssancarerp는 느려진단 말이지? 사이드탭 차량수정 화면 열리는 것도」*

`/ssancar-erp/logs/nginx-access.log` 실측 (요청 5,574건):

```
평균 0.644s · 최대 14.09s · 1초 초과 290건(5.2%) · 3초 초과 248건(4.4%)
livewire/update 5,010건 · 평균 0.536s · 최대 14.09s
```

**느린 요청의 정체:**

```
/provide/api/nice-lookup/   99건 · 평균 8.2초 · 최대 13.6초   ← 외부 NICE API 호출
/livewire-*/update          느린 건들이 NICE 조회와 같은 초에 찍힌다
```

**3초 초과가 몰린 시각** = UTC 00·01·02시 = **한국시간 09·10·11시**(업무 시작, 차량조회가 몰리는 때).

**응답 크기와 상관이 없다** — `~30KB` 요청도 최대 **13.62초**가 나온다.
⇒ HTML 이 커서가 아니라 **워커가 NICE 조회에 8~14초씩 묶여** 뒤 요청이 줄 서는 것이다.

🔑 **CPU 도 메모리도 한가하다** — load average 0.16 (2 vCPU) · 여유 메모리 6.2GB · 스왑 0 · OOM 0.

🚨 **그래서 RAM 을 줄이면 이 증상은 더 나빠진다.** `max_children` 을 줄여야 하는데,
   NICE 동시 상한이 4(§15)라 **워커 6개 중 4개가 묶이면 남는 게 2개**다. 지금은 14개 중 10개가 남는다.

## 5. 🔁 옮길 때 실제로 해야 하는 일 — jin 걱정 3개 중 2개는 기우다

| 걱정 | 실제 |
|---|---|
| **IP 변경 → NICE·공유기·DNS 다 손봐야** | ✅ **Lightsail 고정 IP 를 떼서 새 인스턴스에 붙이면 IP 가 안 바뀐다.** NICE 미들웨어·공유기 화이트리스트·DNS 전부 그대로. 전환 중 짧은 다운타임만. |
| **S3 문서를 매칭시켜 넣을 수 없다** | ✅ **옮길 필요가 없다.** S3 는 인스턴스와 **완전히 별개**다. 새 인스턴스에서 같은 `.env` 키로 같은 버킷을 보면 끝. 파일은 손도 안 댄다. |
| **지금까지 넣은 데이터** | ✅ **48MB 다.** 오늘(09-18) 미리보기 만들면서 **실제로 덤프→전송→복원을 3분에 성공**했다. |

⚠️ **진짜 손이 가는 것은 따로 있다:**

1. **Lightsail 스냅샷으로는 다운사이즈가 안 된다** — 스냅샷 복원은 **같거나 큰 번들만** 된다.
   ⇒ 새 인스턴스를 만들고 **수동 이전**해야 한다(패키지·nginx·php·MySQL·cron·supervisor·인증서).
2. **이 서버에 4개가 산다** — ssancarerp + ssancarboard + NICE 게이트웨이 + 구 Django.
   **전부 같이 옮겨야 한다.** 하나라도 빠지면 3사 차량조회가 죽는다.
3. **SSL 인증서**(Let's Encrypt) 재발급 — 도메인이 그대로면 자동이지만 전환 순서를 타야 한다.
4. **cron·supervisor·systemd 유닛** 재구성 — DB 백업 03:00, 알림톡 스케줄, 큐 워커 2개.
5. **`.env`·APP_KEY** — 🚨 **APP_KEY 를 새로 만들면 RRN 이 전량 소멸한다.** 반드시 복사.

## 6. 💰 득실

**득**
- 월 $44 → **$24 (4GB)** ≈ **월 $20 · 연 $240 (약 32만원)** 절감
- 디스크 154GB → 80GB (실사용 12GB 라 충분)

**실**
- 이전 작업 반나절~하루 + 전환 중 다운타임
- 여유 메모리가 6.2GB → 2.4GB 로 줄어 **피크 여유가 얇아진다**
- 🚨 **실패 시 3사 차량조회가 같이 멈춘다**(NICE 게이트웨이)

**🅿️ 먼저 해볼 것 — 돈 안 드는 것부터**
- 구 **Django(gunicorn) 제거** — 트래픽 0 인데 메모리·디스크를 쓴다([[project_nice_gateway_migration]] 에 이미 대기 중)
- `/var/log` **1.4GB** 정리 (logrotate)
- 이 둘만 해도 이전 시 4GB 여유가 더 확실해진다
